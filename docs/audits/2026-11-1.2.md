## Summary

This is the release audit for 1.2. It reviewed the changes between v1.1.0 and the release candidate bec36a9: Note
Insights (on-device summaries, related notes, the map and topic summaries, and the insights files that sync with the
vault), Make a Copy (`sempere store copy`), the They Match join confirmation, streamed WebDAV uploads on Linux, the 1.1
audit follow-ups, and the release tooling. It found 20 issues: 1 High, 2 Medium, 6 Low and 11 Info. The High finding
(A-06) let a removed device plant insights that every device then showed as written by a current device, by way of the
step that re-sealed a device's own files after a key change. The two Medium findings were a failure memo that kept
notebook and tag names in a plain file outside the vault, and map cluster ids that could crash the app. Every finding
except D-11 was in code that no release had contained (no tag, no TestFlight build, no Homebrew formula), so they are
not vulnerabilities in any shipped version: they get no advisory and no CVE, and they are listed as caught before
release, fixed in 1.2.0. D-11 (Low) is the one item in released versions: after a re-encryption, a storage host could
make a sync run download more than its limit. It is fixed in 1.2.0. The reviewers are AI models and can miss things;
this report is evidence of what was looked at, not proof that nothing else is wrong.

### Out of scope, and why

- **Lane E (web viewer).** No file under `web/` or `docs/web-viewer.md` changed. Whether the viewer ignores an
  `insights/` folder was not checked (`docs/format.md` section 1 says readers that do not implement section 16 ignore it).
- **Device-only behavior.** The on-device language model itself (its tests skipped: the model was "not ready" on the
  review Mac), the background Insights task on a device, the Keychain class of the device key Make a Copy creates, and
  the Face ID prompt before an Add Device "They Match". The code paths are the existing ones; an AI source review
  cannot observe the device.
- **Apple's model assets.** Whether the system's download of Apple's model and embedding assets contacts anything
  beyond Apple, and the policy's "that download contains none of your data", are operating-system behavior.
- **Real servers and providers.** D-09 was not run against Nextcloud or ownCloud, and A-06's copy-in route was not run
  through real iCloud Drive (reproduced with a shared folder, which is what those routes hand the code).
- **Linux runs.** Lane D read the FoundationNetworking paths (chunked PUTs, `needNewBodyStream`, redirects with a streamed
  body) but did not run Docker; the Linux CI job runs them.
- **GitHub-side settings.** The ruleset's bypass actors were not visible to the review account (the API returned
  `null`); App Store Connect's privacy answers and the project website's fingerprint page were not checked.

**Not a finding.** Documented non-goals (`SECURITY.md` "Scope") and design decisions the reviewers considered and left
alone:

- Any current key holder can write an insights file named for another device, the work device's map included. Unlike
  the per-device summaries, insights files carry no per-device signature. Current devices can already edit every note,
  so this gives them nothing new; "one writer per file" in `docs/format.md` section 16.1 is a writer rule.
- A storage host replaying an older valid insights copy, or withholding files: copies are ordered by `written` with a
  7-day future guard, and withholding is availability, which the documents accept.
- They Match lets a user approve without comparing the words. The design states the trade-off and the cost of a partial
  match (`docs/design/1.2-join-confirm.md`), `docs/security.md` says to compare all six, and the delay, warning and owner
  check have no bypass.
- `store copy` makes a writable vault from a source opened with the recovery key, a removed device or an unconfirmed
  list: by design, with notices in the CLI and the app; the copy cannot reach the source's epochs or devices.
- A crash during Make a Copy can leave a Keychain item for a vault id that never existed: an orphan with no data.
- The background Insights pass holds the vault key in memory while the device may be locked: the same exposure as
  background sync, and it needs the vault to have been unlocked first.
- Insights file names show which device processed which note, and when: documented storage metadata (their sizes, which
  were not documented, are G-05).
- Leftover Watch recordings of another vault keep plaintext until the user deletes them: unchanged from 1.1 and
  documented; 1.2 adds a count and Delete on the watch.
- The apt plain-HTTP fallback has no freshness check: the signed Release files still authenticate packages, and it is a
  fallback after two failures, as the script says.
- `X-Expected-Entity-Length` on streamed uploads reveals the body size, which the server sees anyway.

### A-06: Re-sealing a device's own insights files trusts any earlier-key file that bears its name (High, caught before release)

**Claim it breaks.** `docs/format.md` section 16.1: "A removed device, which holds only earlier keys, can therefore
neither read later files nor plant one a reader shows." Also the general rule that files under earlier keys are accepted
only when an epoch record seals them (sections 15.6 and 15.14); this path went around it.

**Attack.** A device removed from the vault keeps the earlier epoch's key. If it can still write into a folder that a
current device reads as its local vault without the sync engine's current-key filter, it writes
`insights/<note>.<B>.insights.age` (or B's map, topics or device file) sealed and tagged under the earlier key, B being a
current device. Two routes reached that state: a vault the CLI opens in place in a shared provider folder, and the first
`sempere store import` or Open Vault copy-in of such a folder, which copied `insights/` as is. On B's next insights pass,
`resealOwn` found a file named for B that failed the current key, opened it under the earlier key, and rewrote its content
under the current key with a fresh `written`. Every device then showed the planted summary, keywords and concepts as B's.
If B was the work device, its planted vectors and map were used by every reader. A planted `gen.slug` on a voice note
whose text the removed device knew was taken by the work device's title step, which picked the best generation from any
device, and written into the note as a title revision. Sync over WebDAV or a folder target, Make a Copy's merge and
restore were not routes: they place only current-key copies, or leave `insights/` out.

**Evidence.** Reproduced at bec36a9 by the lane and confirmed by the verifier. In a three-device test vault (A, B and X),
A removed X; X sealed a note file named for B with its earlier key. Before B's pass, A's snapshot showed nothing; after
B's re-seal, A's snapshot returned the summary "PLANTED BY REMOVED DEVICE" and the slug "PLANTED TITLE" as B's. Real
iCloud Drive was not used.

**Fix.** Nothing is re-sealed any more. After a key change a device deletes its own-named files that open only under an
earlier key, and its ordinary pass writes them again: nothing in the vault shows which holder of the earlier key wrote
such bytes, and insights can be recomputed. The update report lists the deletions under `removed`. Sync no longer
fetches a device's own insights file that exists only on the target; the device's next write replaces it. Regression
tests: `InsightsStoreTests.testEarlierKeyFileNamedForACurrentDeviceIsNeverShown` (the reproduction's shape) and
`testOwnEarlierKeyFilesGoAfterARemovalAndRemovedDevicesFiles`, plus `InsightsUnopenedCopyTests` for the sync side.

**Affected.** No released version: the code arrived after v1.1.0 and was in no TestFlight build. Fixed in 1.2.0, the first
release with Note Insights.

**What to do.** Nothing.

**Severity.** High: given a removed device, it plants content that passes as authentic, which is the High row of the
severity table. The routes were narrow (an in-place CLI vault on a shared folder, or a first copy-in), but the effect
matches the row. The lane and the verifier had rated it Medium; the second reviewer raised it.

### B-03, G-01, A-07: Insights failure memo kept names in a plain file that nothing deleted (Medium, caught before release)

**Claim it breaks.** `docs/security.md` "What the encryption does not protect": the list of plaintext the app keeps on
the device, which said the caches of note insights are encrypted under keys derived from the vault's key and that a
notebook or tag is kept only "as a digest keyed from the vault's key, never a name".

**Attack.** Local, needing the device's files or a backup, not the unlocked app: another local account if the file mode
allowed, backup software, a Mac process outside the container rules, or the CLI's state folder, which is not sandboxed.
To avoid retrying failed generations, Insights kept a memo at `<device state>/Insights/<vault id>-failures.json` (CLI:
`$XDG_STATE_HOME/sempere/insights/<vault id>-failures.json`). It was plain JSON written with the default mode and no
backup exclusion. It held the names of notebooks and tags whose topic summary failed or was emptied by the fact check (a
common outcome), as `notebook:<path>` and `tag:<name>`; note ids with the first 16 bytes of an unkeyed SHA-256 of each
failed note's text, which confirms a guess for short or predictable notes; and a flag for notes the model's guardrail
refused, which marks the notes with sensitive content. Nothing deleted it: not turning Note Insights off, not
`insights purge`, not removing the vault from the device. It also reached device and iCloud backups.

**Evidence.** Confirmed by the verifier from the code (`FailureMemo.swift` save and record paths; no deletion anywhere).
Not run end to end: the debug fake model would need a scripted topic failure. The privacy policy's sentence that turning
Note Insights off deletes them concerns the vault's files and still held.

**Fix.** The memo is sealed under a key derived from the vault key (`LocalCacheKey`, purpose `insights-failures`),
written mode 0600 with file protection, excluded from backups, and replaces a plain file left by an earlier build when it
loads. It is deleted when Note Insights is turned off (the app's switch, a pass that sees it off from any device,
`insights purge`, `sempere settings set insights.enabled false`), when the vault is removed from the device (a store vault
or a WebDAV copy), and by `store remove`. `docs/security.md` names it. Regression tests:
`TopicSummaryTests.testTheMemoIsSealedPrivateAndGoesWhenInsightsIsOff`, `testLoadingDeletesThePlainMemo`, and
`CLIInsightsTests.testTurningOffBySettingsDeletesTheMemo`.

**Affected.** No released version. **What to do.** Nothing.

**Severity.** Medium: metadata (notebook and tag names) reached a party the documents say cannot see it, through
backups. The lanes and the verifier had rated it Low; the second reviewer raised it for the missing backup exclusion.

### A-08 (with B-04): Map cluster ids were not range-checked (Medium, caught before release)

**Claim it breaks.** `docs/format.md` section 9: readers fail with a typed error, never trap, on any byte from a vault
folder.

**Attack.** A holder of the current key (any listed device; a removed one only through A-06) writes a map file whose
cluster id or parent is `Int.min`. The map validation accepted it. Drawing the map then trapped on `abs(Int.min)`: the
app's Note Insights map on every device that read that map, and `sempere insights map --format svg`. The verifier found a
worse case: the map builder numbered new clusters from the previous map's largest id plus one, which overflows when that
id is `Int.max` (or `Int.max - 1`, at the next increment). Because the work device reuses its previous map when the
embedding key matches, every insights pass on the work device trapped before writing a new map, a crash loop that only a
fresh map would clear.

**Evidence.** The lane's test showed the decoder accepting a map with id `-9223372036854775808`; the trap itself was not
executed. The verifier traced the builder overflow from the code. No other id arithmetic was found in the map code;
duplicate ids do not trap.

**Fix.** A map file's cluster `id` and `parent` must be 0 to 1,000,000,000 (`docs/format.md` section 16.7 limits). The SVG
and the app's view pick a color with an index that cannot trap for any id, and a rebuild numbers new clusters from 1
again, carrying no id over, when the previous map's ids leave no room or are negative. Regression tests:
`InsightsFuzzTests.testMapClusterIdsAndParentsAreBounded`, `InsightsPipelineTests.testClusterIdsStayInRangeWhateverThePreviousMapHolds`
and `testTheMapDrawingTakesAnyClusterId`.

**Affected.** No released version. **What to do.** Nothing.

**Severity.** Medium: hostile input crashes the app. In practice it needs the current key.

### B-01: `store copy` removes an existing `--recovery-out` file after refusing to overwrite it (Low, caught before release)

**Claim it breaks.** `docs/cli.md` and the option's help: `--recovery-out` "Refuses to overwrite."

**Attack.** No attacker: data loss from an ordinary mistake. `sempere store copy SRC NAME --recovery-out FILE`, with FILE
already present (another vault's recovery key, a reused path), refused to overwrite it and then, in its error handler,
deleted it unconditionally. Every other failure inside the same block (creating the store folder, opening the source, a
`--strict` stop, the output step) did the same. A deleted recovery key of another vault is lost for good if it was the
only copy. A second, unlikely path: an error while reporting a vault already installed would have deleted that vault's
device key and recovery key.

**Evidence.** Reproduced at bec36a9 with a CLI built from the tree and a synthetic vault: "refusing to overwrite", exit 1,
then the file was gone. The control, `store create` with the same option, kept the file.

**Fix.** A failure removes the `--recovery-out` file only when this run wrote it, and reporting runs after the vault is
installed, so it never removes the installed vault's keys. Regression test:
`CLIStoreCopyTests.testAnExistingRecoveryOutFileIsLeftUntouched`.

**Affected.** No released version (`store copy` arrived in #47, after v1.1.0). **What to do.** Nothing.

**Severity.** Low on the security scale: only the user can trigger it. It was still fixed before release as a data-loss
bug.

### B-02: `store copy`'s passphrase check missed two spellings (Low, caught before release)

**Claim it breaks.** `docs/cli.md` "store copy": the same variable for the source's passphrase and the new vault's is
refused, "and so is `$SEMPERE_PASSPHRASE` serving both when the new vault takes a passphrase."

**Attack.** No outside attacker. The check compared the options as given, not the variable each side actually read (a
side with no variable named falls back to `$SEMPERE_PASSPHRASE`). Two spellings passed:
`--source-passphrase-env SEMPERE_PASSPHRASE` with `--recovery-passphrase` and no `--passphrase-env`, and
`--passphrase-env SEMPERE_PASSPHRASE` with no `--source-passphrase-env` when the source needs a passphrase. Either way the
copy's passphrase copy of its recovery key was sealed under the source's passphrase. When the source is a vault someone
else shared, that person could open the copy's recovery key wherever they can read its storage, which is the case the
rule exists to prevent. The check also wrongly refused two valid cases (a source opened with `--identity`, and
`--generate-passphrase` with `--recovery-passphrase`).

**Evidence.** Reproduced at bec36a9: both spellings exited 0, and in both the source's passphrase opened the copy's
passphrase copy.

**Fix.** The check compares the variables each side reads (an explicit `SEMPERE_PASSPHRASE` included), only when both
sides read one, and also compares the passphrase values themselves. Regression tests:
`CLIStoreCopyTests.testOnePassphraseVariableForBothIsRefusedHoweverItIsNamed` and
`testOneVariableIsFineWhenOnlyOneSideReadsIt`.

**Affected.** No released version. **What to do.** Nothing.

**Severity.** Low: a stated rule fails, but only the user's own choice of options triggers it.

### D-08: Insights files that never open were downloaded again on every run (Low, caught before release)

**Claim it breaks.** None outright: new risk. The nearest documented bounds are the per-run download limit (which held)
and 1.1's refusal stop and "a refusal is saved as it happens, so a killed run does not repeat its downloads", which did
not cover insights.

**Attack.** A hostile WebDAV host, or anyone who can write to the share, with no key, lists any number of valid-looking
insights names (a note id, or a map, topics or device file, with a made-up device id) with junk bodies up to each kind's
bound (64 KiB for a note file, 1 MiB for topics, 8 MiB for a map). An unlocked two-way run with Note Insights on fetched
every one, found it did not open, kept no record, and fetched them all again on the next run, up to the run's download
limit, with nothing in the report. The cost is bandwidth, battery, metered data and run time; nothing is placed or read,
and memory stays at one file at a time.

**Evidence.** Reproduced at bec36a9 against an in-memory remote: 20 junk note files and one 8 MiB map file were read on
each of three runs, and every report was empty.

**Fix.** An insights file only on the target that opens under no key this device holds is recorded (hash, settled
stamp, the key it was tried under) and not fetched again until one of them changes. Each such fetch counts with the run's
refused files, so the refusal stop applies, and it is listed under skipped. A run stopped by a limit keeps the records it
made. Regression tests: `InsightsUnopenedCopyTests` (settled copies are not fetched again, they count as refused files, a
stopped run keeps its records, and own or other devices' earlier-key copies are handled as above).

**Affected.** No released version. **What to do.** Nothing.

**Severity.** Low: repeated cost a hostile host can impose, inside the documented per-run bound.

### D-09: On Linux, a streamed upload a server stored short was moved into place unchecked (Low, caught before release)

**Claim it breaks.** `docs/design/device-first-sync.md` F11 (a cut upload leaves a receiver the old file or the complete
new one), restated in `docs/io.md` for write-once files. `docs/design/1.2-linux-upload-stall.md` named it as a remaining
limit for blobs, but `docs/io.md` did not.

**Attack.** No attacker needed. From #48 the Linux CLI streams PUT bodies, sent chunked, with `X-Expected-Entity-Length`
in place of `Content-Length`. A server that answers 201 to a chunked PUT while storing a short body, and ignores that
header, had its short temporary file moved under the final name. A revision is repaired later when the server lists
sizes; a blob is never repaired by its writer, other devices refuse it by size and hash, and if the writing device is
lost, the attachment is lost to the vault. Before 1.2, Linux PUTs had a fixed length.

**Evidence.** Read from the code by the lane; the verifier confirmed the path and narrowed the claim: only until a 411 or
501 switches the transport to fixed-length PUTs, and sabre/dav (Nextcloud, ownCloud) honors the header, so those
servers should refuse short bodies. Not run against a real server.

**Fix.** After a create-only PUT sent chunked, the client PROPFINDs the new file (Depth 0). When the listed size differs
from the bytes sent, the write fails (the file is deleted under a strong ETag, else left for clean-up), so a short
temporary upload is never moved into place and the next run sends it again. A PROPFIND that fails, a listing without a
length and a replacing PUT (`vault.json`, `settings.age`) are not checked; `docs/io.md` states that limit. Regression tests:
`RevisionUploadTests.testAShortStoredStreamedRevisionUploadIsNotMovedIntoPlace`,
`testAShortStoredStreamedUploadUnderWeakETagsIsNotMovedIntoPlace`, `testAStreamedUploadToAServerListingNoLengthSucceeds`,
and `BlobResumeTests.testAShortStoredStreamedBlobUploadIsNotMovedIntoPlace`, against a mock server mode that stores a
short body and answers 201.

**Affected.** No released version (the streamed PUT is new in 1.2). **What to do.** Nothing.

**Severity.** Low: needs a non-compliant server, and the damage is limited to a writer that is later lost. 1.1 rated the
same class Medium (D-02, D-06) when it affected every server that writes bodies in place; here the verifier narrowed it to
servers that ignore the expected-length header.

### D-11: After a re-encryption, per-device summaries were read every run outside the download limit (Low)

**Claim it breaks.** `docs/io.md` "Bounds per run": every download counts against the run's download limit.

**Attack.** A hostile WebDAV host, or anyone who can write to the share, with no key. Once a vault has finished a
re-encryption, each two-way run checks whether the published per-device summaries files on the target are sealed under a
key from before it. That check read every listed `summaries/` file on every run and never counted the reads against the
run's download limit. Each read was bounded (64 MiB per file), but a host could list many such files and make a run
download more than its limit, again on every run. Nothing is placed, read or exposed.

**Evidence.** Found by the D-08 verifier (`Sources/SempereSync/DeviceSummariesSync.swift:128` at bec36a9: a `read` with no
`budget.downloaded`) and confirmed by the second reviewer. The same code is in v1.0.0, v1.0.1 and v1.1.0. The 1.1 full
audit did not find it.

**Fix.** The check reads each target file once per settled stamp and counts each read against the run's download limit.
Regression test: `ReencryptSyncTests.testSummariesAreNotReadAgainEveryRunAfterAReencryption`. The 1.2.0 changelog
names it.

**Affected.** Sempere 1.0.0 to 1.1.0, the app and the CLI, syncing a re-encrypted vault with a server you do not fully
trust. Vaults that never finished a re-encryption are not affected.

**What to do.** Update to 1.2.0.

**Severity.** Low: a missing bound on cost a hostile host can impose; no confidentiality or integrity impact.

### F-01: Code-owner list left some release tooling and dependency files unowned (Low, caught before release)

**Claim it breaks.** `docs/ci.md` "Trust anchors have a code owner" and 1.1's F-13 follow-up: a seat with write access
cannot change the release tooling or the build's pins without the maintainer's approval.

**Attack.** A seat with write access (an agent, or a stolen token) opens a pull request that changes a file the release
build runs but `CODEOWNERS` did not list; with code-owner review required only for listed paths, it merges on the
ordinary checks. `release-build.sh` copies `ci-linux.sh`, `package-cli.sh`, `smoke-linux-cli.sh`,
`build-linux-static.sh` and `static-sdk-cache.sh` from `main` into the tag's worktree and runs them, so a change there
runs on the maintainer's release host and decides what is packaged. The verifier added files the lane missed: `forge.sh`
(sourced by the release sweep check), `changelog-section.sh` (writes the release notes), `swiftpm-quarantine.sh`
(sourced by `ci-linux.sh`), `local-ci.sh`, the `justfile` and `Package.resolved`. The maintainer still reviews `main` and
signs the tag, so this removed a review gate, not the last check.

**Evidence.** Read-only: the `TOOLING` list in `release-build.sh` against `.github/CODEOWNERS`, and the ruleset (code-owner
review on). `CODEOWNERS` itself was new in 1.2 (#49), so no release was built under the gap.

**Fix.** `CODEOWNERS` lists every script `release-build.sh` copies and runs, what they source, the sweep's forge helper,
`changelog-section.sh`, `local-ci.sh`, the `justfile` and `Package.resolved`. `check-security.sh` gains an owners check
that fails when a `TOOLING` script, or a `scripts/` file an owned or `TOOLING` script sources, has no `CODEOWNERS` line,
with tests in `test-check-security.sh` (#56).

**Affected.** The release pipeline only; nothing shipped. **What to do.** Nothing.

**Severity.** Low: a missing hardening step behind other checks.
