## Summary

This is Sempere's first published audit. It covered all seven areas of the code at commit 6a7afb0 (the 1.1 feature set,
including the Apple Watch voice notes that have never shipped), the documents that make claims about it, the release
pipeline and the privacy policy. It found 44 issues: 1 High, 9 Medium, 11 Low and 23 Info. The crypto and format lane
found no break in the age implementation, the tag checks or the epoch rules it read, only an import slowdown and a zip
hardening gap. The High finding is in the documented web viewer
hosting layout: a person who can write to the vault's WebDAV share, such as a removed device that kept its login, could
run code in the viewer's page if the user opened a link to it. Four of the Medium findings and the High one were handled
as private advisories and are fixed in 1.1.0. The Watch findings (C-01 to C-07) were in code that never reached users and
are fixed before release. Every other finding is fixed in public changes, except one that is
open until the release itself (F-09) and four closed with no change (B-04, E-05, F-10, G-02). The reviewers are AI models and can
miss things. A delta audit of the changes merged after 6a7afb0 found 18 more (2 Medium, 7 Low, 9 Info); none lets
anyone read notes, recover a key or plant content. 13 are fixed in 1.1.0 and five Info items are follow-ups ("Delta audit"). This report is evidence of what was looked at, not proof that nothing else is wrong.

### Out of scope, and why

- **Device-only behavior.** Memory limits (jetsam) on an iPhone, iPad or Watch; the Keychain on a locked watch; the
  Face ID gate; the iOS app-switcher snapshot store; the iOS Local Network prompt; what WatchConnectivity routes through
  Apple when the phone and watch are apart; Universal Clipboard on a real Mac. An AI source review cannot observe them.
  Two were planned as owner device checks; neither was run (see "Method").
- **App Store Connect's App Privacy answers and the live privacy page.** Owner-side, no network from the review. The
  repository's own record says "Data Not Collected"; the code agrees except for G-04.
- **GitHub-side settings.** Private vulnerability reporting and the repository's Actions settings (allowed actions,
  token defaults, fork-PR approval). The API refused the review account (403, admin scope). The owner reviewed the
  Actions settings before release.
- **Third-party services.** Apple's speech model download, crash reports and sysdiagnose sharing, the Homebrew tap's
  service. Only the tap's contents were read (F-09).
- **Safari proper and real passkey providers.** The viewer was tested in Playwright's Chromium and WebKit only.

**Not a finding.** Documented non-goals (`SECURITY.md` "Scope") and design decisions that the reviewers considered and
left alone:

- Anything that needs the unlocked device or the identity file: the open vault holds its key while the app is in the
  background; signing blobs are usable while the device is locked after first unlock (by design, so a locked home device
  can sign); a stolen unlocked phone or watch records notes; the unauthenticated watch provisioning request needs code
  on the paired device.
- Metadata a storage provider sees by design: file names, sizes and times, revision timestamps, device ids and edit
  cadence. Only the documentation gap is reported (G-01).
- age's own non-goals: the recovery script does not check body tags (read-only path, and a storage attacker cannot make
  a file that opens under a key they do not hold); passphrase bytes are not Unicode-normalized, which matches `age -p`.
- Join words are 66 bits: a second preimage must be found online during one join against a commitment that covers the
  attacker's key (design decision, `docs/design/key-hierarchy.md`).
- scrypt work factor 20 (1 GiB) from storage on the passphrase copy: documented, and memory is checked before allocation.
- Storage-provider powers the documents accept: a hostile server can hold back, drop, replay older genuine summaries or
  deny service ("Signed means authentic, not current").
- Plain HTTP to localhost for WebDAV (never leaves the device); a certificate pinned by the user is accepted without
  host-name or date checks (trust on first use is the design).
- `sempere://quick-voice/widget` lets any app or link start or stop a phone voice note: documented, the audio goes only
  into the owner's vault.
- A compromised viewer host, browser or extension (the web viewer's threat model).
- Dev-only npm advisories (10 moderate, in lint tooling that never ships).
- Fork pull requests forging CI pass records: the fork controls its own workflow anyway, and `main` never takes a fork's
  records.
- AirPrint of the recovery kit and Universal Clipboard for ordinary note text: user-initiated system services (a document
  note only for the kit, G-10).

## Method

**Models.** For this baseline run the runbook says Opus everywhere. All seven lane reviewers, all verifiers and the
second reviewer of the triage were Claude Opus (the lane notes name Claude Opus 5.5). The coordinator that pinned the
commit, ran the lanes and wrote the triage was a Claude model too. No human reviewed the source. Every reviewer is the
same model family, so a blind spot shared by that family is a blind spot of this report.

**Deviation from the runbook.** The runbook says one verifier per finding. Verifiers here worked one per lane. Each
verifier saw only the id, title, severity, component and claim of each finding rated Low or above (22 of them), never the
lane's reasoning or reproduction, and built its own reproduction or explained why the claim fails. Verdicts: 21
confirmed, 1 downgraded (E-02, Low to Info), 0 refuted, 0 not reproducible. Findings rated Info were not sent to a
verifier. C-07 was found by the second reviewer after verification and is Info, so it has no verifier either.

**Second review.** A second Opus reviewer checked the coordinator's triage and fix designs and changed four severities:
E-01 Medium to High (the result is a recovered key and its precondition, a removed device that kept its share login, is
the High row's own example); C-02 Low to Medium (it defeats the same documented remedy as C-01 by itself); C-03 Low to
Medium (leftover audio can be sealed into a different vault than it was recorded for); and E-02 Low to Info, which
agreed with the verifier's downgrade. The reviewer also moved B-02 and E-04 into the private fixes (they share code and
text with B-01 and E-01), added C-07 and approved the Medium F-01 for the open track on stated conditions (below). A
third Opus pass reviewed the four private fix commits before release and required two changes (a residual work
amplification in the A-01 fix, and a state file the D-01/D-03 fix left behind). Both were applied before the commits
were accepted.

**Pin and tools.** Commit 6a7afb0c92ba3b1209e1355aa1b5928da120cd5c (main after Watch PR 2, #22). Swift 6.4.2 (swift-driver
1.168.6, Apple Swift version 6.4.2), node v26.12.1, jq 1.7.1-apple, curl 8.7.1 (LibreSSL 3.3.6), age v1.3.2, Docker for the
Linux checks. The web lane used Playwright 1.56.1 (Chromium 1194, WebKit 2215) and vite 8.3.3 in a throwaway clone.

### E-01: Recommended hosting puts a writable share on the viewer's origin (High)

**Claim it breaks.** `docs/web-viewer.md` "Threat model": everything the storage server returns is untrusted and "cannot
make the viewer run code"; the viewer's own files are the only trusted code on its origin.

**Attack.** Someone who can write to the vault's WebDAV share but holds no vault key: a device removed from the vault that
kept its share login, the sync machine, a shared account. The documented layout served the viewer and the share from one
site, so the viewer's Content Security Policy (`script-src 'self'`) admitted a script uploaded into the share. If the
user opened a link to the uploaded page (on the user's own viewer host name, so it looks genuine), the script ran as the
viewer: it could read a key as the user typed or pasted it, read the viewer's stored data and trigger the remembered
key's passkey prompt. The viewer's own code is unchanged; the recommended server setup was the problem.

**Evidence.** Reproduced at 6a7afb0 by the lane and again by the verifier, on loopback with a stand-in for the documented
Caddy site (one origin, basic auth, the documented CSP header, a writable share): the uploaded script ran with no CSP
violation, and synthetic text typed into the real viewer's key field reached the attacker. Not run against a real Caddy,
and not rerun on v1.0.1: the Hosting section of `docs/web-viewer.md` is identical in v1.0.0, v1.0.1 and 6a7afb0.

**Fix.** The hosting section now recommends a separate host name for the share. If one host name is kept, everything
under the share's path is served sandboxed, as a download, with no content sniffing (`Content-Security-Policy: sandbox;
default-src 'none'`, `Content-Disposition: attachment`, `Content-Type: application/octet-stream`,
`X-Content-Type-Options: nosniff`), so an uploaded file is never a document of the viewer's origin. The threat model
states that every path on the viewer's origin must be the viewer's own files or served sandboxed, and that a credential
that can write a same-origin share is as sensitive as the viewer host. The app and the CLI are unchanged. This is a
documentation and server-configuration fix, published with the advisory; no release is needed to apply it.

**Affected.** Anyone who set up the web viewer from the hosting section of `docs/web-viewer.md` in 1.0.0 or 1.0.1 with the
share on the viewer's own host name, where someone other than the owner can write to the share. Not affected: a viewer on
its own host name, a share only the owner can write to, the apps and the CLI.

**What to do.** Change the server configuration as in the updated hosting section, or split the hosts. Change the share's
password if a device that could write to it was removed or lost. If you may have typed or passkey-unlocked a key in the
viewer after following an unexpected link into the share, treat that key as exposed: for a device key, remove that device
from the vault (a new epoch); for the recovery key, replace the recovery kit.

**Severity.** High: the result is a recovered key, and the precondition (a removed device that kept a share login) is the
example the High row of the severity table gives. The verifier had rated it Medium because the user has to follow a
link; the second reviewer raised it because the link is on the user's own viewer host name.

### A-01: Notability transcript reading has no work budget over shared plist values (Medium)

**Claim it breaks.** `docs/format.md` section 9: readers bound the work they do by the size of the input and never expand
shared references into copies.

**Attack.** Anyone who gets a user to import a crafted Notability `.note` file (no key needed). The importer reads each
recording's transcript with a walk that had no work budget over values the file shares between many places, so a small
file keeps the import at full CPU for a long time. No data is exposed or changed.

**Evidence.** Reproduced at 6a7afb0 and on v1.0.1 (d175447). Time grows with the square of the file's reference count: a
2,755-byte plist took about 5.7 s and a 4,755-byte one about 24.6 s; on v1.0.1 an 8,755-byte one took 87 s. The fuzz run
did not find it, because random byte mutation does not build this shape.

**Fix.** Transcript reading shares one work budget across all recordings of a note. Every visited node costs one unit,
and each dictionary costs one unit per entry plus one per 64 bytes of its keys. When the budget runs out the transcript is
not read, and the import report says so for that recording. A regression test and a fuzz seed cover the shape. The fix
review found that long keys were not charged by length in the first version of the fix; that was corrected before release.

**Affected.** Sempere 1.0.0 and 1.0.1, the app and the CLI (`sempere import notability`), when importing a file from
someone else.

**What to do.** Update to 1.1.0. Until then, import only Notability files you made yourself; stop a stuck import by closing
the app, or Ctrl-C in the CLI.

**Severity.** Medium: hostile input exhausts the app, and a stated reader rule fails. No confidentiality or integrity
impact.

### B-01: Tree export `--clean` can act outside `--out` through a linked folder (Medium)

**Claim it breaks.** `docs/cli.md` "Export": the `.sempere-export-<format>.json` manifest is not trusted, so a doctored one
in a shared folder cannot make an export write or `--clean` delete elsewhere.

**Attack.** Someone who can write to the export folder (the documented case is a shared folder) adds a symbolic link to a
folder elsewhere and a manifest entry through it. The owner's next `sempere export --all --format markdown|html --clean`
deletes the named file outside `--out`, and exports write plaintext note files into the linked folder. The guard checked
the text of each path but not whether a path component on disk was a link.

**Evidence.** Reproduced at 6a7afb0 by the lane and the verifier, with a synthetic vault and a CLI built from the code:
a file outside the output folder was deleted, and a note file was written into a folder outside it. Reproduced again on
v1.0.1. The app is not affected (it exports into a fresh private folder and removes the manifest).

**Fix.** Every manifest-driven operation now runs relative to the opened output folder and opens each path component
without following links. An entry with a link anywhere in its path, or whose leaf is not a regular file, is skipped and
reported. `--clean` deletes a file only if its size and SHA-256 match what the export recorded (for an older manifest,
the size and hash its note recorded); any other file is left and reported. Files are written under a temporary name with
mode 0600 and moved into place with `rename(2)` (see B-02). Regression tests plant a linked folder and a doctored entry
and check that nothing outside the output folder changes. The fix review tried link, case, `..`, manifest and hard-link
variants and found no bypass. It left one narrow time-of-check race, which needs a concurrent local attacker with write
access to the export folder, for a hardening change after release.

**Affected.** The `sempere` CLI 1.0.0 and 1.0.1, when exporting into a folder other people or programs can write to.

**What to do.** Update to 1.1.0. Until then, export only into a folder only you can write to, do not use `--clean` on a
shared folder, and check for links with `find DIR -type l`.

**Severity.** Medium: a stated guarantee in `docs/cli.md` fails in a narrower case (needs write access to the export
folder), with file deletion as the result.

### C-01, C-02, C-03: Lost Apple Watch findings (Medium, never shipped)

before 1.1 is submitted.

**C-01. Claim it breaks.** `docs/security.md` "A lost Apple Watch" and `docs/quick-capture.md`: a lost watch can add voice
notes "until the iPhone's key is replaced (a new epoch)". **Attack.** Whoever holds a lost or stolen watch (with its copy
of the iPhone's capture profile) records notes after the owner started a new epoch. When the watch's file reached the phone
over WatchConnectivity, the phone recorded it in its own write ledger under the epoch the file's metadata named, and the
next catch-up re-sealed it under the current key.
Every device then adopted it as the phone's voice note. Turning the setting off did not stop it. **Evidence.** Reproduced at
6a7afb0 (lane test `testAWatchCopyOfTheOldProfileStillPlantsNotesAfterANewEpoch` and an independent verifier test): after
a device removal, a note sealed with the stale profile was accepted and adopted. **Fix.** A Watch file is admitted only
if Use on Apple Watch is on and the file's epoch is the one the phone holds for that vault; otherwise it is held on the
phone only (never in a vault folder, never synced), with Add to inbox and Delete in Settings and
`sempere inbox watch held list|add|delete`. The lost-watch steps in the documents are now: turn the setting off, unpair
or erase the watch, replace the key. The documents also now say that WatchConnectivity can reach the phone through
Apple's relay, not only within Bluetooth range. **Severity.** Medium: the documented revocation fails and someone without a key can
plant content that passes as the owner's; it needs a lost watch that is paired and reachable, and the product was unreleased.

**C-02. Claim it breaks.** The same lost-watch sentences. **Attack.** The owner replaces the key (new epoch) without turning
the setting off first; at the next unlock the phone sent the new epoch's capture key to the paired watch automatically,
re-arming the lost watch. **Evidence.** Verified by code reading and a verifier test at 6a7afb0 (a rotated profile is sent to the
old recipient without a new request). **Fix.** Turning the setting off sends a clear and forgets the watch's key, so
nothing is encrypted to that watch again until a watch asks after the user turns the setting back on. The documents
name the toggle as the first step. **Severity.** Medium (raised from Low): it defeats the same remedy as C-01 on its own.

**C-03. Claim it breaks.** `docs/quick-capture.md` "Plaintext audio": without a profile nothing can seal a recording and it is
deleted. **Attack.** Local only, needs the watch's file system after its first unlock. When the profile was cleared
while a recording was in progress, or a leftover waited, the plaintext audio segments stayed on the watch as long as it
had no profile, and a Reset did not delete them. Leftovers were also sealed with whatever profile came back, so audio
recorded for one vault could land in another vault's inbox, readable by that vault's key holders. **Evidence.**
Reproduced at 6a7afb0 (lane test `aClearedProfileLeavesThePlaintextFolderForGood` and a verifier test). **Fix.** A
recording's manifest names its vault; the watch keeps the profile it started under until the seal, and seals a leftover
only with that profile or a current profile of the same vault. With no profile at all (after a clear or a Reset),
leftovers are deleted, as on the phone. The phone's own sweep checks
the vault too (C-07). **Severity.** Medium (raised from Low): notes could reach a party the documents say cannot see them,
and plaintext stayed on a device indefinitely; rare, and unreleased.

**Who is affected and what to do (C-01 to C-03).** Nobody: not shipped. Watch users on 1.1.0 or later have the fixes.
How far from the phone a watch can still deliver files over WatchConnectivity was not checked on devices; the fix does
not depend on it.

### D-01: Two-way sync buffers several whole revisions in memory at once (Medium)

**Claim it breaks.** `docs/io.md`: a server cannot make the client buffer more than one file's limit.

**Attack.** A hostile WebDAV host, or anyone who can write to the share, lists new revisions near the 256 MiB limit.
A two-way run downloaded several at once (6 by default in the app, up to 16 in the CLI), each read whole, which can
exceed a gigabyte of memory. Progress was saved only at the end of the run, so a run that the system ended for its
memory left nothing saved, and the next run started the same downloads again. No note content or key is exposed: the
files fail their checks.

**Evidence.** Reproduced at 6a7afb0 by the lane and the verifier, and again on v1.0.1: 6 to 16 whole-revision downloads in
flight at once, with the implied peak at the full limit (4 GiB at 16 jobs). Memory use on a real device was not measured.

**Fix.** The side-by-side download follows the partial fetch's rule: only revisions with a listed size of at most 8 MiB
are fetched together, and they are read with that bound, so a server that lies about size fails that one read. Larger
or unsized revisions come one at a time. Each refusal is saved as it happens, so a killed run does not repeat its downloads.

**Affected.** 1.0.0 and 1.0.1, the app and `sempere sync webdav`, syncing with a server you do not fully trust.

**What to do.** Update to 1.1.0. Until then sync only with servers only your devices can write to; if the app keeps
closing during sync, turn sync off for that vault.

**Severity.** Medium: hostile input exhausts the app, and a stated bound in `docs/io.md` fails.

### D-03: Quarantined downloads have no total size bound (Medium)

**Claim it breaks.** `docs/design/device-first-sync.md` section 5.5 bounds the quarantine per path "so a server cannot fill
the disk through one path"; nothing bounded it across paths or runs.

**Attack.** A hostile WebDAV host lists new valid-looking file names with junk bodies on every run. Each refused file was
kept in the quarantine folder, never removed automatically, and a run may download up to 64 GiB. Run after run, this
fills the device's storage, and a full disk breaks saving notes and captures.

**Evidence.** Reproduced at 6a7afb0 and on v1.0.1: the quarantine grew 8 MiB per run with no cap, over three runs.

**Fix.** The quarantine is capped at 256 MiB and 1,000 files per target; past that a refusal is recorded (path, size,
digest, time) and reported "not kept: the quarantine is full". No copy is kept when the device has under 1 GiB free,
and a run stops once it has refused 64 MiB or 1,000 files. The fix review found that a state file the change added was
not removed after some runs; that was fixed before release.

**Affected.** 1.0.0 and 1.0.1, the app and the CLI, with a hostile or shared WebDAV server.

**What to do.** Update to 1.1.0. To free space, delete quarantined files: in the app, Sync Targets, Details and Repair,
Quarantined Files; in the CLI, `sempere store quarantine list` and `delete`.

**Severity.** Medium: hostile input exhausts the device's storage. It breaks a bound the design documented, but not a
guarantee in the user-facing documents.

### D-02: A revision upload cut midway can stay truncated on the server (Medium)

**Claim it breaks.** `docs/design/device-first-sync.md` F11: a cut upload leaves a receiver either the old file or the
complete new one.

**Attack.** No attacker is needed: a dropped connection, a killed app or a server restart during a revision upload. On a
server that writes upload bodies in place (the CI-pinned wsgidav does), the cut upload leaves a truncated file under the
revision's final name. The next run lists it on both sides, so it is never uploaded again; every other device downloads
it, refuses it and never receives that revision, and the writer's copy is the only good one. A hostile server could do
the same on purpose, but it can already withhold any file. No confidentiality or integrity impact: the check refuses the
truncated file.

**Evidence.** Reproduced at 6a7afb0 by the lane and the verifier against a mock server that stores a half body and drops the
connection: runs 2 to 4 uploaded nothing and reported no error, and a fresh device quarantined the file. The real
server was not run (no local install, no network); its source was read.

**Fix.** Revisions upload as blobs already did: to a temporary name, then a move that refuses to overwrite. A move that
finds the name taken counts as success only if the server's file has the same size and bytes. A repair handles damage an
older client left: for a revision both sides list whose server copy is shorter than the local file and a prefix of it,
the client uploads the full file under a temporary name, deletes the damaged copy (only that version when the server
gives a strong entity tag) and moves the new one into place. The run reports it as replaced. Regression tests cover a cut
upload on a revision name and the repair.

**Affected.** 1.0.0 and 1.0.1, syncing over WebDAV to a server that writes bodies in place. A revision already damaged by
an older version is repaired by 1.1.0 on that device's next sync.

**What to do.** Update to 1.1.0 on the device that wrote the edit and sync. If a device was lost between the cut upload
and the repair, that edit is lost to the vault.

**Severity.** Medium: a documented guarantee fails in a narrow case. Open track: it needs no attacker and gains none.

### F-01: Release Linux build reuses a toolchain cache that test jobs can write (Medium)

**Claim it breaks.** `SECURITY.md` "Scope": the release pipeline's integrity; `release-build.sh`: binaries are built from
exactly the tagged sources. The Static Linux SDK is pinned by checksum, but only when it is installed.

**Attack.** Anyone whose code runs in a local Linux Docker job on the maintainer's Mac (the tests of a branch being gated,
a hostile pull request run locally, or a compromised transitive Python package that the WebDAV test job installs, F-03)
could change the installed SDK in the shared cache volume that every job mounts writable. The next local release build
would link the changed libraries into the Linux tarballs that `SHA256SUMS` and the Homebrew formula vouch for.

**Evidence.** Reproduced at 6a7afb0 by the lane (read-only: the test container found the SDK writable) and the verifier
(a throwaway volume seeded from the real one: a file in the SDK was changed from the test image, and the static build
guard accepted it). Whether the real volume was ever changed was not checked.

**Fix.** A static (release) Linux build now runs in fresh Docker volumes that are removed when it ends, and test jobs no
longer mount the SDK volume. The build script removes any installed Static Linux SDK and installs it again from the
checksummed archive, and the images are pinned by digest. F-03's hashed dependencies landed in the same change (#25).
The triage also required the maintainer to delete the two old volumes before the 1.1.0 release build, because the SDK
in them may already have been changed and nobody can tell.

**Affected.** No released binary. v1.0.0 and v1.0.1 were built in GitHub Actions and their attestations verify (see
"Dependencies and release integrity"); no release was built from the local volume. The exposure existed only on the
maintainer's build machine.

**What to do.** Nothing for users. Verify releases as described in `SECURITY.md` "Verifying releases".

**Severity.** Medium: the release pipeline's integrity could fail through a precondition (hostile code in a local job).
Open track: no user was exposed, and the vulnerable state existed only on the build host.

### A-02: Zip entry overlap check does not cover the local header's variable fields (Low)

**Claim it breaks.** `docs/format.md` section 9: no two zip entries whose header and data overlap (else the archive is refused).
**Attack.** A crafted `.note` or package zip: the check ignored the local header's own name and extra-field lengths, so
entries could overlap and the archive was accepted. **Evidence.** Reproduced by the verifier with a 217-byte zip; the
per-archive read budget (32 times the archive size, at least 2 GiB) and the 1 GiB per-entry cap still hold, so this was not
exhaustion. **Fix.** The check reads each entry's local header and uses its real data start and end. **Affected.**
1.0.x imports. **What to do.** Update. **Severity.** Low: a missing hardening step and a document that overstated; bounded
by existing budgets.

### B-02: Re-exported plaintext files keep the mode of the file they replace (Low)

**Claim it breaks.** `docs/cli.md`: exports are written for their owner only, files mode 0600. **Attack.** Local only.
Re-exporting over an existing file (a rerun, a file made by another tool) kept that file's mode, so a 0644 file stayed
readable by other local accounts after receiving new plaintext. **Evidence.** Reproduced at 6a7afb0 and on v1.0.1:
re-exporting over a 0644 file left 644; a fresh export is 600. **Fix.** Each file is written to a temporary file with
mode 0600 and moved over the old one with `rename(2)`, so it keeps mode 0600 (fixed with B-01, GHSA-jg6x-72x7-6vr2). **Affected.** 1.0.0 and 1.0.1: the CLI, and the app's PDF, share and
bulk export when the target exists. **What to do.** Update; `chmod -R go-rwx DIR` after an export. **Severity.** Low: an
unlikely local-only leak.

### B-03: Copy Key on a Mac does not expire the copied recovery key (Low)

**Claim it breaks.** Code and interface contract: Copy Key puts the key on this device's clipboard only and clears it after
three minutes. `docs/security.md` does not state it. **Attack.** Local only. Under Mac Catalyst the pasteboard's
expiry was not honored, so the new vault's recovery key stayed on the clipboard until something replaced it, readable by
any process of the user and by clipboard-history tools. **Evidence.** Reproduced by the lane and the verifier with the
same pasteboard call in an unbundled Catalyst binary (a synthetic string still readable after its expiry, from another
process). The signed app and Universal Clipboard behavior were not tested. **Fix.** On the Mac the app clears the item
itself after three minutes, and when it quits, if nothing else was copied since. The item also carries the
nspasteboard.org concealed and transient markers, which clipboard managers on the Mac skip. **Affected.** The Mac app, 1.0.x. **What to do.** Update; clear
the clipboard after copying a key. **Severity.** Low: a local-only leak.

### C-04: The epoch named in transfer metadata is not checked (Low, never shipped)

**Claim it breaks.** None: new risk (`docs/design/1.1-watch.md` says the metadata "is never trusted"). **Attack.** A
modified watch app names an epoch id the phone never had; the file was placed and ledger-recorded, and catch-up then
reported a problem on every run and never finished, repeating a full scan after each back-off. No content was affected.
**Evidence.** Reproduced at 6a7afb0 (`testAnUnknownEpochInTheMetadataLeavesCatchUpUnfinishedForGood`, verifier test).
**Fix.** The admission rule from C-01: a file for an epoch the phone does not know is held, and Add is disabled for it.
**Affected.** Nobody. **What to do.** Nothing. **Severity.** Low: repeated cost and a standing warning, no content effect.

### F-02: Release build tooling and images are not pinned to reviewed versions (Low)

**Claim it breaks.** None outright: hardening. **Attack.** A moved upstream image tag or an edit in the maintainer's working
tree could change what the release build produces: images were named by tag, and packaging scripts were copied from the
working tree without a check that it is clean or equals `main`. The local image tags did resolve to the CI-pinned image
at audit time. **Evidence.** Read-only, plus `docker images` on the build host. **Fix.** Images are pinned by digest, the
release build refuses to run unless the working tree is clean and its `scripts/` and `packaging/` equal `origin/main`'s,
and `scripts/ci-linux.sh` no longer counts as release-neutral. **Affected.** The release pipeline; no released artifact. **What to do.** Nothing. **Severity.** Low:
hardening.

### F-03: WebDAV test server dependencies are installed without hashes (Low)

**Claim it breaks.** None: new risk. **Attack.** Only the two top-level Python packages were pinned; their dependencies
resolved fresh from PyPI on each run, as root, in a container that mounts the checkout (and, locally, the F-01 cache).
**Evidence.** Read-only. **Fix.** A fully pinned, hashed requirements set installed with `--require-hashes --no-deps`.
**Affected.** The maintainer's build machine and CI; nothing shipped. **What to do.** Nothing. **Severity.** Low: a
test-only dependency channel.

### F-04: Release verification documents promise attestations that new releases will not have (Low)

**Claim it breaks.** `SECURITY.md` "Verifying releases" and the Homebrew README: release tarballs carry build provenance
attestations. **Attack.** None. After v1.0.1 releases are built on the maintainer's Mac and carry no attestation, so the
promise overstated what a user could verify, and the checksums file was unsigned. **Evidence.**
`gh attestation verify` passes for v1.0.0 and v1.0.1; no release script makes one. **Fix.** The documents now say that
v1.0.0 and v1.0.1 have attestations. From 1.1.0, the tag and `SHA256SUMS` are signed by the maintainer's own SSH key
(#25 and #26; "Dependencies and release integrity"). **Affected.** Anyone verifying a release after 1.0.1.
**What to do.** Follow `SECURITY.md` "Verifying releases". **Severity.** Low: a document that overstates.

### G-01: Metadata lists understate what plaintext `vault.json` and file names show (Low)

**Claim it breaks.** `docs/security.md` "What others can see", the privacy policy ("file names, sizes and modification
times") and the tour. **Attack.** Anyone with read access to storage (iCloud Drive, a WebDAV host, a copied backup) reads
`vault.json` and the file tree. Beyond the documented list, they learn the vault's key-change history (the epoch number and
the reason for each change: device removed, home handed over, takeover with the recovery kit, kit replaced), each
device's kind, when and by which device it was added, the vault folder's name, and the exact size of each saved revision
(only attachments are padded). **Evidence.** Reproduced by the verifier on a synthetic vault at 6a7afb0 (the same text is
in v1.0.1). **Fix.** `docs/security.md` lists the fields. The privacy policy and the in-app tour now say that storage
also sees the vault's device list, in one file that is not encrypted. A test pins the plaintext keys of `vault.json` to
the documented list. **Affected.** Everyone, 1.0.x: the
metadata was already visible; only the description was short. **What to do.** Read the updated "What others can see".
**Severity.** Low: a document that overstates. Not Medium, because this is the format's plaintext-by-design metadata, not a
flow the design did not intend.

### G-03: Privacy policy permission list omits notifications and local network (Low)

**Claim it breaks.** Privacy policy "Device permissions": the app asks for a permission only when you use the feature that
needs it, then a list. **Attack.** None. The app requests notification permission for backup reminders, and also with
no local action: when it sees a takeover by another device and when a synced setting turns a reminder on. On iPhone
and iPad a WebDAV server on a LAN address triggers iOS's Local Network prompt, which the policy did not mention.
**Evidence.** Reproduced by the verifier (a synced `backup.reminderDays` value reaches the permission request) and by
code reading; the Local Network prompt is documented OS behavior and was not observed. **Fix.** The app asks for
notification permission only when the user turns on a backup reminder on that device. A takeover notice or a reminder
turned on by a synced setting is shown only where permission was already given. The policy lists notifications and the
local network, and the app now has a usage description for the Local Network prompt. **Affected.** 1.0.x. **What to do.** Nothing. **Severity.** Low: a document
that overstates.

### G-04: WebDAV requests carry the device's preferred languages (Low)

**Claim it breaks.** Privacy policy: Sempere does not transmit any data about you. **Attack.** The WebDAV server's
operator sees an `Accept-Language` header, added by the system's networking, naming the app's language and region on
every request. **Evidence.** Reproduced at 6a7afb0 with a loopback server (the server received the header). **Fix.** The
client sends a fixed `Accept-Language: en`, with a test of the request headers. **Affected.** 1.0.x, WebDAV sync. **What to
do.** Nothing. **Severity.** Low: narrows who the user is beyond what the documents say, to the user's own server only.

### G-05: Imported HEIC images keep location metadata with stripping on (Low)

**Claim it breaks.** Privacy policy: photos you add have their location and camera data removed by default.
**Attack.** None outside the vault. A Notability import stored an embedded HEIC photo as is, with its GPS and camera data,
inside the encrypted vault, readable by every key holder and any tool that extracts the blob. Exports already strip it.
**Evidence.** Reproduced at 6a7afb0 with a synthetic HEIC (the GPS block survived). Whether real Notability packages
contain HEIC was not established. **Fix.** The app's import converts HEIC through the same converter as Add Image when
the photo setting is on, keeping the converter's size and orientation; the CLI, which has no converter, keeps its
per-image warning. **Affected.** The app and CLI import in 1.0.1. **What to do.** Update; re-import affected notes if
needed. **Severity.** Low: a document that overstates; the data stays inside the encrypted vault.

### D-05: A cut `vault.json` upload stops two-way sync on that target (Medium)

**Claim it breaks.** `docs/design/device-first-sync.md` F11. **Attack.** No attacker is needed. A dropped connection while home uploads `vault.json` (approve, rename, label, epoch change) to a server that writes bodies in place leaves it truncated. Every device's two-way run then stops with "not a vault manifest", and the app never repairs it; only a push-only run (the CLI) did. **Evidence.** Reproduced with a truncated server copy. **Fix.** A two-way run that has the vault key and a verified device list replaces a `vault.json` that does not parse, under the server copy's ETag, and only on a target known to be this vault's (it synced there before, or the target's `epochs/` holds the record). A run without the key still refuses it (#34). **Affected.** 1.0.0 and 1.0.1 over WebDAV to such a server. **What to do.** Update. Until then, a push-only sync from a device with the key repairs it. **Severity.** Medium: a documented guarantee fails in a narrow case. Open track: no attacker gains anything.

### D-06: Notebook, join and passphrase-copy uploads are not atomic on WebDAV (Medium)

**Claim it breaks.** F11. The D-02 fix covered revisions only. **Attack.** As for D-02. A cut upload of a notebook record, a join request or the passphrase copy stays truncated and is never uploaded again. Other devices skip the notebook record, and home never sees the join request while the new device's screen says it was delivered. **Evidence.** Reproduced for notebooks and joins. **Fix.** Every write-once upload goes to a temporary name and then MOVEs without overwrite; a name already taken counts only at the same size and hash (blobs, named by their content, as before). A cut copy an earlier version left is replaced, and a join request counts as delivered only at its full size (#34). **Affected.** 1.0.0 and 1.0.1 over WebDAV to such a server; the "delivered" status was new in 1.1 and never shipped. **What to do.** Update. **Severity.** Medium, as D-02. Open track.
