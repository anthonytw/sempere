## Summary

This is the release audit for 1.3. It reviewed the changes between v1.2.0 and the release candidate e37bb21: Ask Your
Notes, Spotlight, Share as Web Page and its viewer, saved tools, the Apple Watch held-note protocol, voice-note titles,
the vault folder conflict merge (`sempere vault conflicts`), folder-target placement, and the release tooling. It found
21 issues: 2 Medium, 5 Low and 14 Info. The two Medium findings (E-01 and E-03) were one gap seen from two sides: a
note shared without dates still carried the transcript's creation time and the audio container's recording times. The
Low findings were a translated topic summary that could wedge a device's topic summaries (A-10), the vault passphrase
accepted as a share passphrase (B-01), Settings text that said a watch dropped a copy it keeps (C-14), a conflict merge
that followed symbolic links (D-12) and an incomplete code-owner list (F-02). Every finding rated Low or higher was in
code that no release contained: some were in internal TestFlight builds installed only by the maintainer. They are
caught before release, so they get no advisory and no CVE, and all are fixed in 1.3.0. One Info item, F-01 (swift-crypto
advisories that also cover the version 1.2.0 shipped), is in released versions: Sempere calls none of the affected
code, so it is not exploitable there either. The reviewers are AI models and can miss things; this report is evidence
of what was looked at, not proof that nothing else is wrong.

### Out of scope, and why

- **Device-only behavior.** Whether a Mac's `.localOnly` pasteboard flag stops Universal Clipboard for the new item type,
  what the system's share menu reports when a Copy finishes, how the system treats the Spotlight index (data protection,
  backup, what Siri or Apple Intelligence reads), and WatchConnectivity's delivery order. They are in "Follow-ups" as
  questions for a device.
- **Apple's models and services.** The on-device language model behind Ask and the translation of questions and answers
  (it is the same model, not the Translation framework), and Apple's download of model assets, are operating-system
  behavior.
- **Real iCloud Drive and real servers.** Lane D could not check whether iCloud Drive syncs a symbolic link inside a
  folder (this bears on how reachable D-12 was), or how file versions download. D-12 was reproduced with a plain folder,
  which is what the merge code is handed.
- **Browsers.** The share page's worker under `file:` in Safari and Firefox was not run (`smoke-share.mjs` exists).
- **App Store Connect and the project website.** The privacy answers and the published privacy page were not checked.
- **Unchanged code.** `Sources/Age`, `Sources/CZlib`, `Epoch*.swift`, `JoinCodes.swift`, the importers, `SemperePDF`
  and `Sources/SempereWebDAV` did not change in the delta and were not re-read. Lane A's rule-by-rule read of
  `EpochChain.verify` and `EpochPrecedence.resolve` is still carried over (see "Follow-ups").

"Not a finding" (documented non-goals considered and left alone):

- Any current key holder can write an insights title, map, vectors or a device record for another device, and so change
  what readers use; this is the same power as editing the notes, and a removed device's files are dropped.
- A capture-key holder can choose a capture's `tz` and `source`: it could already choose its title.
- A hostile share file can carry its own code, because the file is the page; the answer is `sempere share --verify`, a
  stock age check, and sending the passphrase another way (documented).
- A share with work factor 20 needs 1 GiB in the browser, after the recipient types a passphrase into an unknown file.
- The Spotlight index is readable by the system, and on a Mac by any process of the account: documented, opt-in, off by
  default.
- An explicit Copy of an Ask answer uses the plain pasteboard, which Universal Clipboard can carry: a user action, named
  in `docs/security.md`.
- The quarantine of the conflict merge is made with default permissions; it holds ciphertext and file paths, under the
  user's own state folder.
- A watch that holds a held note's sealed copy longer (C-14) is the same exposure class as before 1.3, and the watch
  holds no key that opens it.

### E-01 and E-03 (with E-02, G-05): A share without dates still dated its transcript and recordings (Medium, caught before release)

**Claim it breaks.** `WebShareOptions.includeDates`: "Off: the share carries no date at all". `docs/cli.md` "share",
`docs/web-viewer.md` and the share design: the creation date appears only with `--dates`, and the recipient does not
learn dates or the sender's app version.

**Attack.** None needed: a user shares a note with a recording and does not turn on dates. The recipient, who is the
person the user chose, opens the file and its data. Two things reached them anyway. First, the transcript blob was
copied as stored, so it carried its creation time (to the second), the recognizer's engine string (which can name the
operating system's version) and its language. Second, the audio was shared as stored, and the container's `mvhd`,
`tkhd` and `mdhd` boxes hold the time the file was written, in local wall-clock time. The verifier checked what the app's
own recorder writes: AAC in `.m4a`, with only those times and a gapless-priming tag; no location, no device or model, no
encoder string. Imported recordings keep whatever their container holds, which can include a location when the source app
wrote one (not tested: no sample was available). The watch's own audio path writes zero times.

**Evidence.** E-01 and E-03 were reproduced at e37bb21. The recording record's `started` was scrubbed to the epoch, but the
transcript in the decrypted share was byte for byte the stored one (`created` of the test note, the engine string and the
language), and the audio in the share equalled the stored file, with a creation time of the day it was made. Lane G's G-05
reached the same audio from the privacy side.

**Fix.** With dates off, a recording is parsed and its times zeroed (`mvhd`, `tkhd`, `mdhd`), and its `udta` and
QuickTime `meta` location and creation-date items are removed, in a new parser that reads the container as untrusted
bytes: bounded box lengths, a fixed depth, a box-count cap, the same output length as the input, and a refusal for a file
it cannot read whole (the share then leaves that recording out and reports it as skipped, instead of sending it
unscrubbed). The scrubbed bytes are hashed again, so references by recording id still resolve. A transcript is encoded
again with `created` set to the epoch and `engine` empty; the recognized text's engine name is blanked too. The share and
viewer documents now say which containers are scrubbed (the app's and the watch's) and what an imported container may keep.
Regression tests: `AudioMetadataTests` (a fixture recorded the way the app records, plus a fuzz target), and
`WebPageShareDatesTests`.

**Affected.** No released version: `sempere share` and the share page are new in 1.3. Some internal TestFlight builds
contained the share path.

**What to do.** Nothing. If you shared a note without dates from an internal build, the recipient could see its
transcript's time and the recording's time.

**Severity.** Medium: metadata reached a party the documents said could not see it, which is the Medium row's wording.
The lane and the verifiers had rated it Low (the recipient is someone the user chose, and the leak is one time near the
recording time); the second reviewer raised it, because a Low is for wording that overstates, not for metadata that
crosses. Because the code was unreleased, the track and the CVE outcome are the same.

### A-10: A translated topic summary was not held to the topics file's limit (Low, caught before release)

**Claim it breaks.** `docs/format.md` section 16: a topic summary is at most 4,000 characters, and a file that fails its
checks is ignored whole by every reader.

**Attack.** None: a runaway or repetitive answer from the on-device model, when a topic summary is translated into the
user's insights language. The note path cut its translation to the file limit; the topic path did not, and the writer did
not check what it sealed. The file was then written over the limit, every reader (this device included) rejected it, and
the device refused to replace its own unreadable topics file, a guard meant to protect damaged data. Topic summaries from
that device then stopped, and a language change, a map rebuild, new members, a forced run or Regenerate did not help. Only
deleting insights (Purge, or turning Note Insights off and on) or a finished re-encryption cleared it.

**Evidence.** Reproduced at e37bb21 with a scripted model that returned 4,096 extra characters: after one pass this
device's topics were unreadable ("invalid: topic summary") and the second scope in the same pass was already refused.

**Fix.** The topic translation is cut to the topic limit like the note path. Every insights file is now decoded and
checked before it is written, so no writer can emit a file that its readers reject. A file at this device's own name that
fails its content check (but is not damaged) is replaced; a damaged one still blocks. Regression tests in
`InsightsTopicLimitTests` (an extension of `InsightsUpdaterTests`, so a `--filter` on the class name matches nothing).

**Affected.** No released version: v1.2.0 had no translation of topic summaries, and the paragraph was capped at 1,200
characters. Only derived, recomputable data was lost.

**What to do.** Nothing.

**Severity.** Low: availability of derived data. No key, confidentiality or integrity guarantee is affected, other
devices' files stay readable, and the trigger is uncommon.

### B-01: `sempere share` accepted the vault's own passphrase as the share passphrase (Low, caught before release)

**Claim it breaks.** Not a stated guarantee: `store copy` refuses a passphrase variable that serves both sides, and
`share` had no such rule.

**Attack.** The user chooses the reuse. The recipient then learns the vault's recovery passphrase, but still needs the
recovery key file from the vault's storage to use it.

**Evidence.** Reproduced against a debug CLI at the pin: `share --share-passphrase-env SEMPERE_PASSPHRASE` and
`share --passphrase-file` with the same text both wrote the file with exit 0 and no warning; the same text then opened the
vault with the recovery key file.

**Fix.** `share` refuses a share passphrase equal to a passphrase this process read for the vault, or taken from the
variable the vault's passphrase uses, with exit 2 and a message that says how to choose another. A generated passphrase
skips the check. The help says exactly what is caught ("one the vault was opened with"): a recovery passphrase typed into a
file while the vault opens with a device key is not. Regression test in `CLIShareTests`.

**Affected.** No released version (`share` is new in 1.3).

**What to do.** Nothing.

**Severity.** Low: defense in depth. The user chooses the reuse, and the recipient needs the recovery file too.

### C-14: Settings text and documents said the watch drops a held note's copy (Low, caught before release)

**Claim it breaks.** Settings: "Held Watch notes are kept only on this iPhone, not on the watch". Also
`docs/quick-capture.md`, `docs/security.md` and the 1.1 watch design: the watch drops its copy at the acknowledgement.

**Attack.** None: the text understated where copies exist. Since the 1.3 held-and-release protocol, the phone answers a
held note `held`, not `acked`, and the watch keeps the sealed file until the note is added or deleted. The watch cannot
open it (it holds no vault key), but a lost watch keeps it, and deleting the app does not remove it; a re-paired watch
resends a held note the phone no longer lists.

**Evidence.** Verified by reading the Settings string, three documents and the design's own later section (3.6), which says
the opposite of its section 3.4, against `WatchReceiver.ack`, `WatchOutbox.markHeld` and `WatchHeldAckTests`.

**Fix.** The Settings sentence (English and Spanish), `docs/quick-capture.md`, `docs/security.md` and the design now say
that the watch keeps the held note's sealed copy until you add or delete it.

**Affected.** No released version: v1.2.0's outbox had no held state, and its text was true then.

**What to do.** Nothing.

**Severity.** Low: a document that overstates. The exposure class (sealed ciphertext on a watch the user may lose) is the
same as before 1.3, over a longer window.

### D-12: The conflict-version merge followed symbolic links in the destination path (Low, caught before release)

**Claim it breaks.** `docs/io.md`: a hostile folder's links are never followed.

**Attack.** `sempere vault conflicts --merge` copies files a version holds into the vault folder when the folder lacks
them. The listing recorded a symbolic link as present and did not descend into it, so every file a version had below the
link counted as missing; the placement then checked only the leaf, and its folder and temp-file steps resolved links in
the middle of the path. Someone who can change the folder (a provider, or a syncing device) could make the merge write
files into a directory outside the vault.

**Evidence.** Reproduced at e37bb21: with `notes/<id>` replaced by a link to an empty outside directory, the merge
reported the link as skipped and wrote both revision files into the outside directory.

**Fix.** Placement checks every component of the path to the file (before staging and again before writing), refuses a
file below a link, and makes missing folders one level at a time, each checked to be a real folder. Regression test in
`VaultFolderConflictsTests`.

**Residual.** The check and the write are separate path walks, so a writer that swaps a checked folder for a link between
the two is still followed. `docs/io.md` now says the check is made just before the write and that a concurrent writer
racing it is out of scope. Placing by directory descriptor (`openat` with `O_NOFOLLOW`, `mkdirat`, `linkat`) is open for
after 1.3.

**Affected.** No released version (the merge is new in 1.3; CLI only).

**What to do.** Nothing.

**Severity.** Low: the bytes written are files that already passed the received-file check (ciphertext under the vault's
key, or a join request that parses and names this vault), at names fixed by the version, with no read and no overwrite;
the merge is an explicit command.

### F-02: Code-owner list did not cover the web dependency lock or the share viewer's build inputs (Low, caught before release)

**Claim it breaks.** The `CODEOWNERS` header: an agent seat cannot change "the release tooling, the dependency pins, the
security policy or the CI itself" without the maintainer's approval.

**Attack.** A write-access seat changes `web/package-lock.json`, regenerates the 250 KB minified share template, and
passes the CI template check without code-owner review, while a change to `Package.resolved` needs one. The lock was
unowned in 1.2.0 too, but before 1.3 it fed no shipped binary.

**Fix.** `CODEOWNERS` now lists `web/package.json`, `web/package-lock.json`, the share viewer's sources and the template
build script and its inputs. The app's `Package.resolved` copy inside the Xcode workspace is also a dependency pin and
is still unowned (the gap predates 1.3; see "Follow-ups").

**Affected.** No released binary was built from an unreviewed lock.

**Severity.** Low: a missing hardening step and a header that overstates.

### Info findings

- **A-11.** Topics files gained a `gen.outLang` member that `docs/format.md` did not describe and the reader did not
  bound; the derived title's order rule omitted the future window the code applies. The field is now bounded and both are
  documented.
- **A-12.** Found by lane A outside its lane and rated by the second reviewer. `WebPageShare.make` accepted a scrypt work
  factor of 1 to 30 while the viewer opens at most 20 (and has no lower bound). A factor of 21 to 30 would make a file the
  viewer cannot open; one below 17 would make the passphrase weaker against an offline guesser. No shipped caller sets it

(`spotlight.pass` logs a domain and a code; the bundle-bit code logs a role and an errno; the sync-target package line
logs a content type and a flag). The raw error interpolations in the delta are CLI messages to the user's own terminal, not
logs. Ask has no log site.

**Telemetry.** None.
