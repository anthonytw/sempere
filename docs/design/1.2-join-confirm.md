# Confirm instead of typing to join (1.2)

Status: design, 2026-11-13. Part of joining by approval (key-hierarchy.md §6.2, §6.2.1; format.md §15.12;
nearby-join.md). Paths are relative to the repository root.

## 1. Goal

Today the user reads six words on the new device and types them on home, then reads six reply words on home and
types them on the new device. The change: both screens show the words, and the user taps "They match" on each, as in
Bluetooth numeric comparison. Typing and the QR code stay as the fallback.

Non-goals: changing the commitment, the reply digest, the request or reply formats, or the nearby protocol. Nothing
on disk or on the wire changes.

## 2. What exists today

- The new device computes its words and QR text from its keys: `AppModelCore.joinCodes` and `JoinCodes.words`
  (`Sources/SempereAppCore/AppModel/AppModel+JoinDevice.swift:126`, `Sources/Sempere/JoinCodes.swift`). The six words
  are the first 66 bits of the request's commitment, as BIP-39 words.
- Home lists pending requests: nearby ones kept in memory (`nearbyRequests`) and those in the copy's `joins/`
  (`pendingJoinRequests`, `AppModel+JoinDevice.swift:339`). Each row shows the device name, kind and a "Nearby" mark
  (`AddDeviceSheet`, `Apps/Sempere/SempereApp/JoinViews.swift:289` on). The words are never shown on home. Home
  has a text field and a scan button (`JoinViews.swift:387-393`).
- Approval is `approveDevice(words:qr:)` (`AppModel+JoinDevice.swift:394`): it finds the request whose commitment the
  typed words or the scanned code name (`Vault.joinRequest(words:qr:)` and `Vault.joinRequest(in:vaultId:words:qr:)`,
  `Sources/Sempere/VaultDevices.swift:59-73`), checks the owner (`ownerAuthenticator`), then calls
  `Vault.approveDevice(_ request:)` (`VaultDevices.swift:143`), which already takes a request, not words. It returns
  the six reply words and a QR text.
- The new device, once listed, shows `JoinStage.confirming` and asks for home's six words or its QR code
  (`JoinDeviceView`, `JoinViews.swift:123-190`). `confirmJoin(words:keys:)` (`AppModel+JoinDevice.swift:275`) calls
  `Vault.confirmJoin(words:)` (`Sources/Sempere/VaultCheck.swift:366`), which computes the reply digest from the
  vault's id, the device's commitment, `manifest.root` and `manifest.epochId`, and refuses on a mismatch
  (`VaultError.replyMismatch`).

Both directions already reduce to "compute words on one side, compare with words on the other"; today the comparison
is done by typing. So the model change is small: home may approve a request it already holds without typing, and the
new device may compute its own reply words and show them.

## 3. Design

### 3.1 Home approves a request by tapping

- Each pending request row shows its six words (`JoinCodes.words(request.commitment)`), large and numbered, in the
  same layout the new device uses (`SixWordsView`). The device name stays, secondary. A row has "They Match" and
  "Decline". The words are what the user compares; the name is chosen by the sender and proves nothing.
- New model entry `approveDevice(request: JoinRequest, proceed:)`. It is `approveDevice(words:qr:)` after the lookup:
  the same lock, owner check, `requireWritableVault`, `Vault.approveDevice(request)`, `adoptReopened` and
  `nearbyApproved`. The two entries share one private body, so no check is duplicated. The request is one the model
  itself listed (`pendingJoinRequests`), identified by its commitment; the tap names that commitment, never a file
  name (names are the sender's to choose, nearby-join.md N2 and its review).
- The typed field and the scan button move under "Type the words instead" in the same sheet. They call the existing
  `approveDevice(words:qr:)`. Their behavior (waiting for a request that has not arrived: `requestArriving`,
  `requestNotArrived`) is unchanged, which is one reason they stay: a join through the sync folder where the request
  has not arrived yet shows no row to tap.

### 3.2 The new device confirms by tapping

- At `.confirming` the screen shows the six reply words the device computes from what it holds, and "They Match".
  New package function `Vault.joinReplyWords() -> [String]` (the same computation as `confirmJoin(words:)`, factored
  out; it needs `deviceEntry`, `manifest.root` and `manifest.epochId`). The tap calls `confirmJoin(words:)` with
  those words; the check inside then passes by construction, so what the user compares is the only check, as in the
  typed route.
- "Type the words instead" and the scan button stay (`replyWords(fromQR:keys:)`, `AppModel+JoinDevice.swift:291`).
- The words are computed only after the listed `vault.json` is read; nothing is shown from an unlisted state.

### 3.3 What both screens say

Home: "Do these six words match the ones on the new device? Approve only a device you hold." The new device: "Do these
six words match the ones on the device that approved you?" Both say "Compare all six words". "They Match" is not enabled
for 1.5 seconds after the words first show, so a double tap on arrival cannot confirm.

### 3.4 CLI

The screens read and change no vault data beyond what `Vault.approveDevice` and `Vault.confirmJoin` already do, and
the CLI has those through the typed route: `sempere devices approve (WORD x6 | --qr TEXT)` and `sempere device
confirm WORD x6` (`docs/cli.md`). A join through the CLI stays typed. Add `sempere devices approve --id ID`, taking a
request listed by `sempere devices` (its commitment prefix), only if the CLI has no way to approve a listed request
today; read `Sources/SempereCLI/Devices.swift` first. Add `sempere device confirm --show` to print the words the
device computes only if a test needs it; the comparison by tap is an app screen.

## 4. Security: what the tap is worth

The words are the commitment's first 66 bits. They exist so that a request cannot be replaced by another device's
without the user noticing (key-hierarchy.md §6.2 step 2). Typing forces the user to read all six words from the other
screen. A tap does not: a user may look at one word, or none.

Threat model: an attacker who knows the vault id, so can reach home's nearby listener, or who controls the sync target,
and who wants home to approve its own key.

- The attacker sees the real request (nearby, the link is not encrypted, nearby-join.md N2; in storage, it holds the
  file). It then sends home a replacement request with its own key and needs the replacement's words to look right to
  the user.
- If the user compares all six words, the attacker needs a second preimage of 66 bits: about 2^66 key generations
  (design §6.2). That is out of reach.
- If the user compares only the first k words, the attacker needs about 2^(11k) key generations. Each is an X-Wing
  key and an ML-DSA-65 pair; assume 10^3 to 10^5 per second on a cluster (an assumption, not a measurement). The
  attacker learns the real words only when the real request is sent, so it cannot grind ahead of time, but it has the
  minutes the user takes. At 10^5 per second for 5 minutes (about 2^25 tries), one word (2^11) and two words (2^22)
  fall and three words (2^33) do not.
- If the user compares nothing, any device that reaches home first gets approved. This is the case typing prevents and
  a tap does not.

Conclusion: confirm equals typing only when the user really compares, and then only if they compare about three words or
more. The interface can nudge but not enforce. It is the trade Bluetooth's numeric comparison makes, with a longer
code. The design therefore does not shorten the code: a numeric code of 6 digits (about 20 bits) would fall in seconds
to the same grinding. A short code would need a commit-then-reveal exchange (as the short authentication string in
ZRTP), which changes the protocol and is out of scope.

Mitigations in the design, none a guarantee:

- All six words are shown, large and numbered, in the same layout on both screens, so comparing is as easy as it can
  be made.
- A pending request is chosen from rows that each show their words, so a user cannot tap a row without seeing them.
  The row's name is secondary, so a spoofed name does not catch the eye first.
- The owner check (Face ID or the password) still comes before the approval, so a stray tap is not enough.
- The approval changes nothing the typed route would not change. What an unauthorized approval costs is unchanged:
  it adds a device to the vault, which the device list and its history show and which removal with re-encryption
  undoes (design §5.2).
- On the new device the reply words check that the vault is the one home approved, not a vault a storage provider
  made up (§6.2 step 4). A tap without comparing weakens that check the same way.
- There is no "always approve" setting, and the tap is never reachable from an unattended path (a notification
  action, a widget, a shortcut).

The honest sentence for the in-app text and `docs/security.md`: "Tapping They Match is as safe as typing the words
only if you compare them. Compare all six."

## 6. Open questions, with recommended answers

1. **Six words or a shorter code?** Six words; see section 4.
2. **Replace typing?** No. Keep typing and the QR code as the fallback, behind "Type the words instead". They are the
   only way when the request has not arrived at home (no row to tap) and for a user who wants the stronger check.
3. **Does the reply side also become a tap?** Yes, for the same reason: otherwise the join is a tap on one device and
   a typing task on the other. Same fallback.
4. **Is a nearby request treated differently from one that came through the sync target?** No. Both are rows with words.
5. **Should "They Match" need a long press, or a quiz (pick the third word)?** No. A quiz makes the tap a typing task
   again and annoys honest users; the delay and the layout are the nudge.
