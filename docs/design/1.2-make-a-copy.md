# Make a Copy… of a read-only vault (issue #12) (1.2)

Status: design, 2026-11-13. Paths are relative to the repository root.

## 1. Goal

For a vault that opens read-only, offer "Make a Copy…": a new, writable vault of the user's own, with the same notes.
The app (File menu and the read-only banner) and the CLI both offer it. The source is never changed.

Non-goals: keeping the source's revision history, device list, sync targets, settings or inbox in the copy; merging a
copy back into its source (they are different vaults and `vault merge-copy` refuses them, format.md §1.3); copying
while the source is only partly downloaded (a partial copy, format.md §1.2, is refused).

## 2. What "read-only" means here

Four causes make `AppModelCore.isVaultReadOnly` true (`Sources/SempereAppCore/AppModel/AppModel+ReadOnly.swift:46`).
Content is readable in all four; what differs is how faithful a copy can be.

| Cause | Code | Readable | Faithful copy |
| --- | --- | --- | --- |
| Opened with the recovery key (or its passphrase copy) | `isRecoveryOpen`, `VaultError.recoveryKeyReadOnly` (CLI exit 7) | everything | yes |
| This device's list does not check: no confirmed root (the demo vault, a pasted key), a refused list | `listProblem`, `needsVaultConfirmation`, `VaultError.untrustedList` (CLI exit 6) | everything the key opens | yes, with the note that the list is untrusted (see section 6, question 5) |
| This device was removed or is not on the newest list | `unlistedNotice`, `VaultError.removedFromVault` | what its keys open: notes of the epochs it held | partly: later epochs are unreadable; the copy reports them |
| Newer format: a later `format`, unknown `features`, or a newer revision (format.md §7.3, `ReadOnlyLatch`, fixture `Fixtures/newer.sempere`) | `readOnlyReasons`, `VaultError.readOnly` | what this version understands | approximate: skipped ops and elements are lost (format.md §7.4) |

Reading a read-only vault is allowed and a byte copy of its files is too (§7.3), but a byte copy is the same vault
(same id, same `vault.json`, the recovery key's wrap): not "a vault of your own", and still read-only for this device.
So the copy is a new vault whose notes are written fresh.

## 3. Design

### 3.1 One shared core

`VaultCopier` in the package (`Sources/Sempere/VaultCopier.swift`, Linux-tested), called by the app and the CLI.

```
VaultCopier.copy(from source: Vault, into destination: Vault, options:, progress:, cancellation:) throws -> CopyReport
```

- **Source** is any `Vault` that can read (`canRead`): opened with a device key, the recovery key, or in the middle of
  a newer-format latch. The copier only reads: the note reader and `ReducedNote` the exporters use (the exact entry point
  is chosen in the PR), and `readBlob`/`streamBlob`; it never calls
  `requireWritable` on the source, and a test hashes the source tree before and after.
- **Destination** is a vault made by `VaultCreation` (new id, new recovery key, this device home), through the store's
  staging so it appears complete or not at all: `VaultStore.create(name:build:)` runs `build` inside
  `<store>/.staging/<uuid>/` and installs by one rename (`Sources/Sempere/VaultStore.swift:262`). A crash, a cancel or a
  failed note leaves nothing but the staging folder, which `sweep` removes. That makes the copy atomic, and "resume" is
  "run it again".
- **Per note**, one at a time (memory bounded by one note, as `BulkExportSession`; CLAUDE.md "Bulk export"):
  1. Reduce the source note to its current state (the `ReducedNote`, with tombstones dropped, newer content skipped
     and counted).
  2. Write it to the destination as **one checkpoint delta** named "Copied from <source label>" (format.md §5.8.1;
     imports are checkpoints too, so thinning keeps it), built with the same `NoteOps` builders the importers use:
     `addPage` with page size and paper, `addStroke` for live strokes in order, `addItem` for items, `setMeta` for
     title, tags, notebook, favorite, `lang`, `markersBehindText`, `addRecording` and transcripts. Stroke and item ids
     are kept (they only have to be unique in a note). Note ids are kept (question 3). A stroke's `rec` and an
     `audio` item's `recording` resolve inside the note, so they stay valid.
  3. Copy every blob the written ops reference: read through the source note's reference (`readBlob` or `streamBlob`,
     which check framing, hash and keyed name), write to the destination note with `Vault.writeBlob(note:contentsOf:type:)`
     before the delta that names it (CLAUDE.md "Attachment blobs"). A blob that cannot be read is a note failure
     (below), never a dangling reference. Video and audio stream; nothing is held whole.
- **Notebooks**: the records under `notebooks/` (format.md §14) are read and written for the notebooks the copied notes
  use. **Not copied**: `settings.age` (device and vault settings stay the new vault's own), `inbox/`, `joins/`,
  `epochs/`, `keys/`, sync targets, summaries and caches.
- **Writing as the user's device**: through `Vault.apply`/`NoteWriter` with the machine's `DeviceState` or the app's
  `DeviceClock`, one revision per note, so the write ledger and the one-writer rule hold (CLAUDE.md "One revision
  writer"). `CopyReport` is `Codable`: notes copied, pages, strokes, items, recordings, blobs and bytes; notes
  skipped with a reason; for a newer-format source, per note the skipped ops by name and the count of newer revisions
  (the same facts `NoteSummary.newer` carries).
- **Failures**: a note that cannot be read or copied is listed in the report and left out; the copy still completes
  unless `--strict` (CLI) or the sheet's "Stop on the first problem" is set, in which case the whole staging build is
  discarded. A copy with skipped notes says so in its result and is never presented as complete.
- **Deleted notes** (Recently Deleted) are skipped unless `--include-deleted`; they are written in their deleted
  state.

Why not the existing import or export paths:

- Export (`sempere export`) is lossy by design (PDF, PNG, JSON, Markdown); the JSON export is not an import format.
- `store import` and `vault merge-copy` copy files and keep the vault's identity.
- `VaultImporter` (`Sources/SempereImport/Importer.swift`) is the pattern to follow, and a Sempere-to-Sempere importer
  could be registered in `BuiltInImporters`. Recommendation against: the importer registry is the removable-importer
  seam for foreign formats (`scripts/check-importer-isolation.sh`), and this copier is core. It reuses the same builders
  and the same `ImporterProgress`/`ImporterCancellation` shapes without joining the registry.

### 3.2 CLI first

`sempere store copy SOURCE NAME (--recovery-out FILE | --recovery-key FILE) [vault init's recovery options]
[--identity FILE | --passphrase-env VAR] [--include-deleted] [--strict] [--dry-run] [--store DIR] [--json]`
next to `store create` and `store import` (`docs/cli.md`; `Sources/SempereCLI/Store.swift`). `SOURCE` is a vault folder
or a store vault id; the source key is a device key file, the recovery key (`--identity`), or the passphrase copy, as the
other read commands take them. The destination options are `store create`'s, so a copy gets its own recovery kit the same
way a new vault does. `--dry-run` reads everything, writes nothing and prints the report. `--json` prints `CopyReport`.
Exit codes follow the table in `docs/cli.md`: the source's read-only state is not an error here (that is the point), a
partial copy is exit 1 with the report, and a source that cannot be read at all keeps its own code (6, 7).

### 3.3 The app

- `MenuCommand.makeCopy` (File ▸ Make a Copy…; shortcut and enabling in the one place, `MenuCommandTests` checks
  clashes), enabled for an unlocked vault whose notes are all local (not a partial copy), and a button in the read-only
  banner (`AppModel.readOnlyBanner`, `NoteListView`) that opens the same sheet.
- The sheet reuses New Vault's recovery-key step (`VaultLibrary.create`; this device home, the standard kit, the
  optional passphrase copy), a name field defaulting to "<name> Copy", the "include deleted" toggle, a progress bar from
  `CopyReport` counters and Cancel. On success it offers "Open the Copy". A newer-format source shows the report's
  "might be missing something a newer version wrote" lines before the copy starts.
- Model logic is in the library (`AppModel+MakeCopy.swift` in SempereAppCore, on `AppModelServices`, with the
  `generation` re-check after every await); the app word the typed result.
- It never reads a vault in place (CLAUDE.md "Every vault the app opens is an in-app copy"): the source is the open store
  vault.

## 4. Tests

All but the sheet run on Linux.

- `Tests/SempereTests/VaultCopierTests`: copy `sample.sempere` and `items.sempere`; for every note the destination's
  reduced state equals the source's by pages, live strokes, items, meta, recordings (the comparison ignores clocks and
  revision names); every blob hash matches and is reachable through the destination's reference; the destination
  verifies (`Vault.verify`) and the recovery script opens it; the source tree's file hashes are identical before and
  after (the read-only guarantee); a recovery-key-opened source, a source with an untrusted list, and
  `Fixtures/newer.sempere` (skipped ops are reported by name, the copy is not marked newer and is writable);
  a deleted note with and without `--include-deleted`; a note with an unreadable revision (listed, others copied;
  `--strict` leaves no vault); a cancel in the middle leaves no vault and a staging folder `sweep` removes.
- A fuzz seed for the copier's inputs is not needed (it reads through the existing bounded readers) but the property
  "copy of a copy equals the copy" is cheap and goes in.
- `Tests/CLITests`: `store copy` with `--json`, `--dry-run` writes nothing, exit codes, the recovery output file is
  written once, `--strict`.
- `Tests/SempereAppCoreTests/AppModel` on `TestHost`: `makeCopy` from a read-only vault of each cause, progress, cancel,
  the generation check when the vault closes mid-copy.
- App: the sheet's states (`SempereAppTests`), the menu enabling, one `LaunchSmokeUITests` step for the new sheet
  (CLAUDE.md "Launch smoke tests"), Spanish strings (`scripts/l10n.py merge`), `scripts/check-help.py`.
- `docs/cli.md`, `docs/io.md` and the user guide's page for read-only vaults are updated in the same PR; a changelog
  fragment names the feature.

## 5. Security and privacy

- The copy's keys are new: a new vault id, a new recovery key, this device's key. Nothing of the source's wraps, device
  list or signing keys carries over. The new vault is post-quantum like every vault.
- A read-only source opened with the recovery key means the person holds the recovery key; a copy gives them a vault
  they can write, which is the intent. The copy's recovery kit is a fresh secret the sheet makes them save as New Vault
  does.
- The copy's plaintext exists only in memory, one note at a time, never in a temp file except the blob streams the
  existing blob code already stages.
- Revision history of the source is not copied, so edits the source's authors wanted to forget do not travel.

## 6. Open questions, with recommended answers

1. **Keep history or copy the current state?** The current state, one checkpoint per note. History would need the source's
   device ids, clocks and acceptance rule to make sense in a vault that has no such devices (format.md §5, key-hierarchy
   §5.3), and the issue asks for "the same notes".
2. **Copy deleted notes?** Not by default; a flag and a toggle include them.
3. **Keep note ids?** Yes. They are unique within a vault, CLI users name notes by id prefix, and nothing links two
   vaults by id. Recommendation against fresh ids: it breaks a person's habit of naming a note by prefix across the
   source and the copy.
4. **A newer-format source: copy what is understood, or refuse?** Copy, after a warning that lists what was skipped.
   Refusing leaves a person who cannot update the app with no way to keep their notes writable.
5. **An untrusted list (the demo vault's case): allow it?** Yes: the copy reads note content the key opens and the
   copy's own trust starts at its own creation. The sheet says that the source's list was not confirmed. A note whose
   revisions fail their tag checks is a note failure.
6. **A partial copy of a WebDAV vault (notes not downloaded)?** Refused with the existing "download first" path; the sheet
   offers to fetch the missing notes (`downloadNote`) and then copy.
7. **Where does the kit go?** Same as New Vault. No new storage place.
