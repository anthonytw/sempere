## Code PR

### C-10: a paired watch can fill the held-notes cap

Today: the phone holds Watch notes it cannot place (`WatchHeldStore`, `Sources/SempereCapture/WatchHeld.swift`) up to
200 files and 500 MB in all (`maxFiles`, `maxTotalBytes`, lines 67-68; `hold` throws `.full` past either, line 141).
A note held for an unknown vault or an unknown epoch (`WatchHeldReason.unknownVault`, `.unknownEpoch`: those can only
be deleted, never added, `canAdd` line 23) counts against the same cap as notes the user can still add. So a watch
that keeps sending notes for a vault the phone does not hold can use the whole cap, and a note the user could add is
then refused. A file without its sidecar is never listed (`scan` lists by sidecar, line 119) and so is never counted
or removed; the `hold` code removes it only when the sidecar write fails in the same call.

Plan:
- A separate small cap for the two unaddable reasons: 20 files and 50 MB, counted in `hold` from the existing sidecars
  by reason. Past it, `hold` throws a distinct `WatchHeldError.fullUnplaceable`, and the intake reports it like `.full`
  (the watch keeps the note). The general cap stays 200 files and 500 MB and counts every held note, so the small cap
  is a sub-limit, not extra space.
- A sweep for files without a sidecar: in `scan` (or a new `sweepOrphans()` called from the same places that list), a
  `.capture.age` file in a vault folder with no valid sidecar and older than 24 hours is deleted; a file younger than that may be
  a `hold` in progress (the file is written first, the sidecar second, line 152), and the store's lock covers both, so
  a held lock means "in progress" and the age rule is only a second guard. A sidecar without its file is already ignored; it
  is removed by the same sweep.
- The CLI (`sempere inbox watch held list`) shows the counts per reason and the orphans removed.
- Tests (`SempereCaptureTests`, Linux): fill the small cap with unknown-vault notes and show a note for a known vault is
  still accepted up to the general cap; the sub-limit in bytes and in files; orphan removal after 24 hours and not
  before, with an injected clock (`now:` is already a parameter); a sidecar-less file under a held lock is kept;
  `WatchModelTests` for the report the phone shows.

### D-07: no cut-revision repair without a listed size

Today: the repair of a cut upload an older client left under a final name (`repairCutRevision`,
`Sources/SempereSync/SyncEngine.swift:1830`; `repairCutFile`, line 1804) starts only when the server's listing gives the
file a size below the local file's (`entry.size`, `listed < have`). A server whose listing gives no size for a file
never gets the repair, so a revision cut by 1.0.x on such a server stays cut, and other devices keep refusing it.

Plan:
- When a revision both sides list has no listed size, do one bounded verification per (target, revision) instead of
  none: `serverHolds`-style check of the server's copy against the local file, reading at most `local.count` bytes
  (`transport.read(path, maxBytes:)`, already used by `repairCutFile`), charged to the run's download budget
  (`budget.downloaded`). If the copy is a strict prefix of the local file, repair it as today (`placeWriteOnce` with
  `damaged:`). If it is complete or differs otherwise, record it as verified.
- Verified revisions are recorded in the target's sync state (a set of revision keys with the local file's size and
  a digest of its listing entry), so the check runs once per revision, not every run. The set is bounded (entries and
  bytes), and a revision this device did not write is not checked (the damage was this device's own cut upload, and
  only a device that still holds the file can repair it). The per-run cap on verification reads is a fraction of
  `SyncLimits`' download bytes, so a vault with many sizeless revisions is verified over several runs.
- No new network call shape: it is the same bounded GET the repair already makes.
- Tests (`SempereSyncTests`, with the memory store and a scripted remote whose listing omits sizes): a truncated server
  copy is repaired; a complete one costs one read and is never read again; the budget stops the pass and a later run
  continues; a copy that is not a prefix is left alone and reported; a revision the device did not write is not read.
  The WebDAV job (`scripts/test-webdav.sh`) gets one case against wsgidav through the fault proxy with sizes hidden.

### Review follow-up: nearby handshake eviction

Today: at most 4 connections may be in their handshake at once, and a new one ends the oldest
(`AppModelCore.handshakeLimit`, `handshakes`, `handshakeOrder`, `Sources/SempereAppCore/AppModel/AppModel+NearbyJoin.swift:68-92`).
A device that opens connections very fast can keep ending the others' handshakes. The review accepted this as Low and
asked to consider one handshake per remote address.

Plan:
- Give `NearbyJoinConnection` an optional `remoteHost: String?` (a default of nil in the protocol extension; the app's
  `NWNearbyConnection` fills it from `NWConnection`'s current path remote endpoint host, without a port or interface
  scope; the memory transport's tests set it).
- Rule: a new connection from an address that already has a handshake in progress ends that address's oldest one first
  and takes its slot. Only when the address has none and 4 are in progress does the global oldest end. So one address
  can hold one slot at most, and three stay for others. A connection with no known address is its own group.
- It is not a defense against an attacker with many addresses (address rotation, many devices): the rest of the
  design (the proof of the vault id before anything is sent, the short handshake timeouts, the cooldown, nearby-join.md
  L5) is what limits that. The plan says so in `nearby-join.md`.
- Tests (`NearbyJoinModelTests`, `MemoryNearbyTransport`): one address opening ten connections holds one handshake
  and the other devices' three survive; two addresses hold one each; unknown addresses behave as before; the oldest
  of the same address is the one ended; real sessions that finish are not counted.

### Review follow-up: Watch leftovers whose manifest names no vault are never reported

Today: `WatchRecorder.sweep()` seals a leftover recording only with a profile of the same vault; one that started
under another vault, or whose manifest names none (its manifest save failed), stays as it is, never sealed into a vault
it may not belong to (`Sources/SempereCapture/WatchRecorder.swift:261-300`). Such a leftover stays until a clear or
Reset, and no screen or log says it is there. Only a folder with no recorded byte is removed.

Plan:
- `sweep()` returns, with the sealed notes, a count and total size of the leftovers it kept and why (no vault, another
  vault), as a value the watch model and the iPhone's Watch settings show: "2 recordings could not be placed" with
  Delete. No names, no content.
- The iPhone side lists them the way held notes are listed (`WatchSettings`, one row per leftover, size and when), with
  Delete. The watch app shows the count on its Settings page.
- No automatic deletion: a recording is the user's data. A leftover older than 30 days is mentioned once more in the
  report (the only change to the retention rule), not removed.
- Tests (`SempereCaptureTests`, `WatchModelTests`): a leftover with no vault and one with another vault are reported and
  kept, the count survives a relaunch (it is computed from the folders, not stored), Delete removes exactly that
  folder, an empty leftover is still removed silently.

## Tooling PR

### F-13: the signing trust anchor has no review rule of its own

Today: release tags and the release checksum list are verified against `packaging/allowed_signers`, read from
`origin/main` by the release scripts (`scripts/release-tag.sh`, `release-sign.sh`, `release-publish.sh`,
`release-verify.sh`); whoever can merge to `main` can change who is trusted. No `CODEOWNERS` file exists. The
fingerprint is in `SECURITY.md`, in the same repository.

Plan:
- Add `.github/CODEOWNERS` naming the maintainer for `packaging/allowed_signers`, the release scripts above,
  `SECURITY.md` and `.github/`, and turn on "require review from Code Owners" in the repository ruleset for those
  paths. This changes who may merge such a PR (the maintainer, not an agent seat), which is the point; docs and code
  PRs are unaffected.
- A check in `scripts/release-check.sh` (Linux, CI job `release`): the PR gate fails if `packaging/allowed_signers`
  changes without the PR description naming it under a `## Signing keys` heading (the template gains the section), so a change
  cannot ride in a larger PR unnoticed. `scripts/test-release-check.sh` covers it.
- Publish the key fingerprint outside the repository too: on the project website's security page and in the GitHub
  release notes' standard footer, so a reader can compare three places. `SECURITY.md` says where. A change of key then
  needs a change in all three, and the release notes of the release that rotates it say so.
- Tests: `test-release-check.sh` cases (a change with and without the heading; a change to an unrelated file).

### F-14: the apt fallback mirror is plain HTTP and misses arm64

Today: `scripts/apt-install.sh` switches the image's sources to `http://azure.archive.ubuntu.com/ubuntu/` after two
failed attempts (line 13, 20-26). It is plain HTTP, and that archive has no arm64 packages (arm64 lives on the ports
archive), so an arm64 job's fallback fails after its sources are rewritten. apt still checks the signed Release files,
so integrity holds; what plain HTTP gives up is privacy of what is fetched and no protection against an on-path party
withholding or replaying old (still validly signed) indexes.

Plan:
- Choose the mirror by `dpkg --print-architecture`: amd64 keeps the Azure mirror, over HTTPS if that host serves it
  (unverified: confirm with a request when writing the PR; if it does not, keep HTTP for amd64 and say so in the
  script's comment); arm64 uses Ubuntu's ports archive (`ports.ubuntu.com/ubuntu-ports/`), also HTTPS where available. The image
  needs `ca-certificates` for HTTPS, which the install of it comes from the same archive: the script installs it first
  from the image's own sources before switching, and falls back to HTTP if it is absent.
- Set `Acquire::Check-Valid-Until=true` explicitly so a replayed old index is refused.
- A test: `scripts/test-apt-install.sh` with a fake `apt-get` and `dpkg` on `PATH` (the way the other script tests stub
  tools) that fails twice, and checks the rewritten URL per architecture and that the script's exit status follows
  `apt-get`'s.

### F-16: the error-text lint matches only some variable names

Today: `scripts/check-security.sh` flags a performance-log call (`PerfSink`) that interpolates an error's text, but
only for a variable named `e`, `err` or `error` (`String(describing: e)`, `\(error)`, `localizedDescription`; the awk at
lines 154-156). A catch-bound variable with another name (`failure`, `problem`, `$0` in a closure) passes the lint.

Plan:
- Extend the lint to the names the code actually binds: any name bound in the same file by `catch let NAME`, `.failure(let
  NAME)`, `case .failure(NAME)`, a closure parameter typed `Error`, or declared `NAME: Error` / `NAME: any Error`, plus the
  implicit `error` of a bare `catch`. The awk collects those names per file in a first pass and tests the statement against that list.
- Keep `scripts/security-allow.txt` for reviewed exceptions, each with a reason.
- Tests: `scripts/test-check-security.sh` cases for each binding form, each with a log call that interpolates it (must
  fail), one that logs only a count or an enum case (must pass), and a name that merely resembles an error (`errorCount`
  must pass).
- Run the extended lint over the tree in the PR and fix or allow-list what it finds; that list goes in the PR
  description by count, not by content.

## Open questions, with recommended answers

1. **Small cap for unaddable Watch notes: how big?** 20 files and 50 MB, inside the general 200 and 500 MB. A watch that is
   merely paired with the wrong vault rarely holds more than a few notes; the number is a guess, so it is a constant with
   a test, easy to change.
2. **Delete orphan files after 24 hours or at once?** After 24 hours (the intake's file-then-sidecar order makes a young
   orphan normal).
3. **Verify sizeless revisions on every run or once?** Once per (target, revision), recorded in the sync state and bounded.
4. **Code-owner review for the trust anchor: does it block agent seats?** Yes for those paths, deliberately. The seat
   opens the PR and the owner merges, as the project already does for gate changes.
5. **Per-address handshake rule or something stronger?** Per address. A stronger rule needs authentication the protocol
   does not have before the request (nearby-join.md N2).
6. **Report unplaceable Watch leftovers only, or delete them after a time?** Report only. Deleting a recording the user
   made, on a timer, is the wrong default.
