# Design: on-device note insights (Sempere 1.2, headline feature)

Status: reviewed 2026-11-09, decisions below; revised the same day for two owner changes (D5
synced, comparable embeddings; rules by capability, not device). **Revised 2026-11-13 for the owner's
review (D13-D19, §11): one designated work device, transcripts and voice-note titles in, no device
steps, real-note quality runs, 1.1 sync bounds, availability gates, topic summaries behind the cut
line.** Where §11 and an earlier section differ, §11 wins. Release 1.2. No repo was changed.
Labels: [M] measured in the spike (the 2026-11 spike's report), [I] inferred, [C] checked
against code or `docs/format.md` at `main` at the time of review.

## 1. Goal and non-goals

**Goal.** Each note gets a short summary, keywords and concepts, made by Apple's on-device model on
any device where it is available, and an embedding that is comparable across the vault's devices.
They make notes findable ("my dynamics note from last year"), connectable (related notes, a map
built once and shared) and summarizable by notebook or tag. A device without the model (for example
an older iPad without the model) shows every result and still embeds and places its own new notes.

**Non-goals.**
- Titles for ordinary notes (owner: not worth it). Voice notes do get one (D14).
- Private Cloud Compute, Siri AI, ChatGPT or any model that leaves the device. Banned by test (§8).
- Exposing notes to Siri or Core Spotlight (the first option in the 2026-11 research).
- Replacing the source text. Summaries are a gist, never the source of formulas [M: d06 dropped a term].
- A new `sempere/N` major or a `features` entry (D1).

## 2. What exists today [C]

- Search text: `PageText.texts(of:)` (`NoteSearch.swift:35`): recognized handwriting, text boxes, PDF
  text, LaTeX. Recognition is derived data that does not move the modified date (§5.5).
- `features` makes older writers read-only and an unknown op or `setMeta` field is rejected
  (§7.2-7.4), so insights in deltas would make every 1.0/1.1 device read-only.
- **Unknown root entries, as built** (§1: "ignored, never deleted"): `SyncEngine` acts only on known
  root names (no upload, download or delete of `insights/`); push-only `--delete-extraneous` prunes
  only inside `notes/`, `att/`, `epochs/`, `joins/`; `CloudScan` fetches only known files;
  **copy-merge and backup copy only known files** (the draft's "byte for byte" was wrong, harmless);
  `vault verify` calls it `unknownFile`, healthy; re-encryption and its finish skip it, so an old home
  leaves `insights/` under the old key (§3.3); collection and compaction look only under `notes/`.
- Precedent: `summaries/<device>.sealed` (§12.5), ordered by `version` so files relayed between two
  targets settle (`DeviceSummariesSync.swift`), and deleted below a finished re-encryption
  (`Vault.removeSummariesBelowReencryption`, review of #89 S1: the same leak §3.3 closes).
- Note deletion is a restorable `deleteNote` flag (§5.2); revisions stay in the vault.
- Per-device caches (§10.1) are sealed under HKDF keys from `K_e`. Background work goes through
  `BackgroundSyncRequest` (`AppLifecycle.swift:92-118`; headless `NoBackgroundSyncScheduler`).
  Settings have per-type blocks (§13.2). Apple frameworks behind `#if canImport` in `Sources/` have
  precedent (`SempereSpeech`, `VisionText.swift`).

## 3. The design

### 3.1 Tiers, by capability

| Tier | Needs | Output | Stored | Who |
|---|---|---|---|---|
| 0 | core code | TF-IDF keywords, related-by-keywords | no, on the fly | every device |
| 1 | `NLEmbedding` sentence model (no Apple Intelligence) | embedding; the map | the **map device's** vectors and map, synced (§3.8) | every device that supports the pinned revision embeds; one builds the map |
| 2 | Foundation Models, `SystemLanguageModel.default.availability == .available` | summary, keywords, concepts | vault sidecar, synced | every device where the model is available |

The rule is capability, never device type: a device with the model generates; every device that supports the pinned embedding revision embeds;
a device without the model reads the others' summaries. A note not yet summarized shows tier-0
keywords and "Summary will appear after a device with Apple Intelligence has processed this note".
Power policy is per platform (§3.7).

### 3.2 Where insights live: one sidecar per note and computing device

Rejected: insights in deltas (needs `features` or a newer revision, so 1.0/1.1 devices go read-only;
grows history) and one vault index (rewritten whole, ~1 MB per 1000 notes, and two writers conflict).
**Chosen:** one small file per changed note, one writer per file.

```
insights/<noteId>.<device>.insights.age    one note's summary/keywords and/or vector, written only by <device>
insights/map.<device>.insights.age         the map device's key, canaries, clusters, layout (§3.8)
insights/device.<device>.insights.age      a device's supported embedding revisions and canaries (§3.8)
insights/topics.<device>.insights.age      that device's notebook and tag summaries (§3.4)
```

`<noteId>` is the lowercase UUID, `<device>` the writer's id in the vault (§15.4, as in §12.5). All
are replaced whole (atomically, under `VaultFileLock` so the app and the CLI on one machine never
interleave). A note sidecar is written by a generating device (`gen`) and by the map device (`emb`);
usually that is one file per note. A reader takes `gen` from the best file (hash equal to the note's
current hash, then the later `written`) and `emb` only from the map device's file.

Vectors ride in the note sidecar, not a per-device vector file: a changed note costs one ~3 KB write
instead of rewriting about 1 MB (700 notes x 512 x Float16, base64) on every edit.

"Never conflicts", made precise: different writers never share a name, so iCloud never makes a
conflict version between devices. Copies of the *same* file still need an order, because a device
syncing two targets relays others' files (the bug fixed in `DeviceSummariesSync`). The order is
`written`, then the larger SHA-256 of the file, like §12.5's `version`.

### 3.3 Encryption, epochs and deletion

- **Encryption** [C §13.1, §15.2]: an age file to the **current epoch's** vault identity `v_e` (one
  stanza), plaintext the §4 body framing with label `insights` and the file name in the tag:
  `Tag = HMAC-SHA256(tagKey, "sempere/1" ‖ 0 ‖ "insights" ‖ 0 ‖ <file name> ‖ 0 ‖ gzipBytes)`. Same
  keys as note content, stock-`age` recoverable (`tail -c +38 | gunzip`). The tag binds the name, so a
  file renamed onto another note or device fails.
- **Read only under the current key.** A file that does not decrypt and verify under the current
  `v_e` and `tagKey` is ignored (not taken through the chain, not in sealed sets, not in the write
  ledger). This keeps sidecars out of §15.14's acceptance machinery and means a removed device,
  which holds only earlier keys, can neither read new sidecars nor plant ones a reader shows.
- **Re-seal on a new epoch.** When a device first holds a key newer than its own sidecars' (unlock,
  or a verified epoch change), it re-seals its own files under the current key from its insights
  cache or by opening them with the earlier key the chain gives it. No model work. Until then other
  devices see that note as unprocessed (tier 0/1 still work).
- **Delete below a re-encryption.** After a finished re-encryption (§15.8), a 1.2 device deletes every
  sidecar that opens under a key from before it, locally and on each target where its list stands, in
  the same step as `removeSummariesBelowReencryption`. This is what makes "re-encrypt everything" true
  for insights even when an **older app was home** and its pass skipped `insights/`: the leftover files
  (readable with the old key, e.g. a replaced recovery kit) live only until a 1.2 device next syncs.
  Sidecars named for a device that was **removed** (it appears in an earlier list of the vault's chain and is absent
  from the current one) are deleted at once by any 1.2 device, and only in a run where this device's own `vault.json`
  stands on the target (the gate §3.5 applies to pushes). A device on an older list never deletes the sidecar of a
  device it has not heard of: that device may have just joined. Test: a device on an older list does not delete a
  just-joined device's sidecar.
  All of this applies to map files and device records as to note sidecars.
- **Tombstones.** A device "removes" its sidecar by replacing it with a tombstone: the same file
  without `gen` and `emb` and a later `written`, so a bridging device cannot bring the old one back. It does so
  when the note is deleted (§5.2; restore regenerates), and when its sidecar is stale while another
  device's is current (so a summary of erased text does not linger).
- **Turning the feature off** (`insights.enabled` false): every 1.2 device deletes all of `insights/`
  locally and on its targets, and syncs none while it stays off; the insights cache goes too.
- Bounds: 64 KiB on disk and after gunzip for a note sidecar, 1 MiB for a topics file, 8 MiB for
  a map file, 64 KiB for a device record (§9). A file
  that does not verify, parse or validate is ignored, never an error.

A removed device keeps what it could read before (as security.md says) but cannot read later files.
A listed device could forge a file named for another; it can write revisions too, so this only
falsifies labels (no signature, unlike §12.5, whose files gate removal warnings).

### 3.4 JSON

```json
{
  "format": "sempere-insights/1",
  "noteId": "6f1c2b9e-0a43-4f6e-9a51-2c8d7e3b4a10",
  "device": "a1b2c3d4",
  "written": 1764727900000,
  "hashBasis": "text/1",
  "lang": "en",
  "gen": {
    "hash": "9f2c4e1d7a0b3c58e6d1f4a2b7c90e13",
    "model": "afm-ondevice", "os": "27.2", "prompt": 3,
    "summary": "Free vibration of a damped spring-mass system ...",
    "keywords": [ { "t": "damping ratio", "w": 0.82 } ],
    "concepts": [ "critical damping", "logarithmic decrement" ],
    "dropped": 1
  },
  "emb": {
    "hash": "9f2c4e1d7a0b3c58e6d1f4a2b7c90e13",
    "key": { "model": "nl-sentence", "lang": "en", "rev": 1, "input": 1 },
    "dim": 512, "enc": "f16le-base64", "v": "..."
  }
}
```

- `gen` and `emb` each carry their own `hash`: the map device re-embeds at once on a text change
  (0.3 s) while generation waits for a power window.
- `emb.key`: model, language,
  pinned revision, and `input`, Sempere's text-cleaning revision (D11). Float16 [M: identical
  neighbours and clusters].

- `format`: one per-file version marker, as §12.2 does; a reader skips a file whose `format` it does
  not implement. Additive members need no new format (readers ignore unknown members; the only writer
  of a file rewrites it whole, so nothing needs preserving). No `$minReaderVersion`: that §13.4
  pattern exists for a file many writers merge, which this is not.
- `written`: Unix ms, `max(now, previous + 1)` per device; at most 7 days ahead of the reader's clock
  (as §12.5's future window), else unordered.
- `gen.hash`, `emb.hash`: first 16 bytes (32 hex) of SHA-256 of the insight text: `PageText.texts(of:)` joined by
  `\n\n`, NFKC, whitespace runs collapsed, trimmed. A recognition re-run that changes no text, an undo
  or a compaction does not invalidate it. `hashBasis` versions that definition (like `basis`, §5.5).
- `gen` and `emb` both absent = tombstone. `model`+`os`+`prompt` identify generation (FM has no public model version
  [M]). Current when `prompt` equals the reader's and the `os` major matches; otherwise stale: shown
  greyed ("made with an older model") and recomputed in the background (D10).
- Size: about 1-1.5 KB for `gen`, 1.4 KB more with `emb`.
- Topics file: `format`, `device`, `written`, and `topics`: a list of `{ "scope": {"notebook": path}
  | {"tag": key}, "members": n, "membersHash": <hex of SHA-256 over sorted noteId:hash pairs>, "gen":
  {model, os, prompt, at, summary} }`. Scope names stay inside the ciphertext.

### 3.5 Sync and the other vault paths (1.2)

- **WebDAV and folder sync (`SempereSync`)** learn `insights/`, modelled on `DeviceSummariesSync`:
  one `PROPFIND` of `insights/` per run; own files go up (local is the truth), others' files are
  copied to the side that lacks them only when they open under the current key, and the later
  `written` wins where both differ. Unlocked runs only (locked runs and staging skip `insights/`). A
  device pushes insights only in a run whose `vault.json` stands on the target, so a lagging or
  removed device never puts old-key files back.
- **iCloud:** `CloudScan` requests `insights/` items; a conflict version of a sidecar (two installs
  with one device id) resolves to the later `written`, the other copy removed (`ConflictVersions`).
- **Copy-merge:** copies sidecars the vault lacks or holds with an earlier `written`, after the
  checks above.
- **Backup/export: excluded.** Insights are recomputable derived plaintext; a backup is smaller and
  carries less of it. A restored vault regenerates.
- **`vault verify`:** lists sidecars as hints (open/stale/unreadable), never unhealthy.
- **Read-only vaults** (§7.3): no insights write, with the usual message.

### 3.6 Old apps and the `features` question (D1)

No `features` entry. A 1.0/1.1 device ignores `insights/` everywhere, never deletes and never rewraps
it (§2). Its three hazards: (1) *an old home re-encrypts and leaves old-key files*: readers ignore
them and the first 1.2 device to sync after the finish deletes them; residual window documented in
security.md, accepted (the owner's devices all run 1.2). (2) *An old device deletes a note*: a
restorable flag; the revisions stay too, so the sidecar exposes nothing new; 1.2 readers hide it and
its writer tombstones it. (3) *Derived plaintext*: same keys and trust boundary as the notes. A marker
would only make pre-1.2 devices read-only, for no added safety.

### 3.7 Who computes, and when

Capability decides what a device does; the platform decides when.

- **Generation (tier 2):** any device where `SystemLanguageModel.default` is available. **Embedding
  (tier 1):** every device that supports the pinned revision: the map device for every note (§3.8),
  others for notes the map device has not embedded yet, or their whole local set when incompatible.
- **macOS:** a utility-QoS `NSBackgroundActivityScheduler` activity while on power, thermal state
  below `.serious`, vault unlocked. `sempere insights update` does the same headless (launchd
  optional, the owner's choice).
- **iOS and iPadOS:** `BGProcessingTask` with `requiresExternalPower = true`, network not required, as
  `BackgroundSyncRequest.insights` (Info.plist permitted identifier); also foreground while charging
  and not in Low Power Mode. Saves after every note, stops cleanly on expiration: about 50 notes per
  5 minutes at ~6 s each [M]. Embedding a new note (0.3 s) runs in the foreground at once.
- **Order and eligibility:** notes edited in the last 30 days newest first, then by modified date;
  eligible once the hash has been unchanged for 10 minutes and the note is not open in an editor.
- **No coordination protocol for generation.** With `insights.compute = auto`, a macOS device
  generates at once; an iOS or iPadOS device generates a note only if no current `gen` exists after 24
  hours (a battery policy, not a capability rule). Duplicates are harmless (best file wins, the loser
  tombstones itself when stale).
- **Settings** (`settings.age`, §13; new keys in `docs/settings-sync.md` and the schema):
  `insights.enabled` (bool, vault-wide; off deletes, §3.3), `insights.compute` (`auto` | `never`, in
  any type block), `insights.mapDevice` and `insights.embeddingRevision` (§3.8). Settings shows "Processed 412 of 520 notes",
  "Summaries made on: <device names>" and "Map: from <device>, compatible" from the files.
- **Failure:** model unavailable, busy, or language unsupported (`supportsLocale` with `meta.lang`):
  skip and back off; embedding still runs if NLEmbedding has the language.

### 3.8 Shared vectors and the shared map

**Measured on this Mac** (the 2026-11 spike's determinism run) [M]: the sentence and contextual
embedders are bit-identical across runs and processes; `currentSentenceEmbeddingRevision` = 1 and
the supported set is {1}; the contextual model (revision 1, a `modelIdentifier`) is compiled per chip,
so cross-chip numbers may differ; Float16 keeps neighbours and k-means clusters identical (min cosine
0.99999994). The iOS simulator runs neither embedder, so cross-device agreement is **untested** until
owner check 0 (§9).

**The embedder.** `NLEmbedding.sentenceEmbedding(for:revision:)` at an explicit **pinned revision**,
never "current". Sentence, not contextual: better in the spike [M] and probably not chip-compiled
[I]. A vector's key is `{model, lang, rev, input}` (plus `modelId` if a contextual model is ever used).

**The map device.** One device builds the shared vectors and map: the one named by the shared
setting `insights.mapDevice`, which must support the pinned revision. Unset, a supporting device
claims it by writing its own id (macOS at once, iOS or iPadOS only if no map file exists after 24
hours; §13.3's per-slot merge settles a race identically everywhere). The user can move it; if its
map file is older than 14 days, any supporting device may claim it. A device that loses the role
deletes its map file and stops writing `emb`; readers take vectors only from the map device.

**Device records.** Every device with Note Insights on writes `insights/device.<device>.insights.age`
(at most daily, and when its OS or supported set changes): `supported` sentence revisions per
language, OS version, whether the generation model is available, and its canary vectors at the
pinned revision. "Recently seen" = written within 30 days by a device the current list has.

**The pin: lowest common denominator.** The shared setting `insights.embeddingRevision` (per
language, e.g. `{"en": 1}`) names the revision. When it is unset, the first map build sets it to the
**lowest** revision every recently seen device supports, and writes that to the setting. After that
the pin **never moves by itself**:

- **Upgrade (manual).** When a recently seen device supports a newer revision, Settings and `sempere
  insights status` offer "Use the newer embedding model", listing the devices that do not support it
  ("iPad Pro (no Apple Intelligence) will stop making vectors and can't place new notes until a
  supporting device processes them"). On confirm the pin moves up; if the map device lacks the new
  revision the role moves to one that has it; the map device re-embeds every note once (about 4
  minutes for 700 notes) and rebuilds.
- **Down (manual).** The same screen offers an older common revision, with the same kind of warning.
- **A device that does not support the pin** (after an upgrade, or one that joins later) is a
  **vector reader**: it reads the synced vectors and map, makes no vectors, places nothing, and its
  new notes show "pending" until the map device embeds them, as summaries do. Status says so.

Readers use only vectors whose key equals the map file's `key`. The map device writes the map last,
so during a one-time re-embed the notes it has already moved simply show as pending until the new map
lands; nothing is mixed.

**The map file** (`insights/map.<device>.insights.age`):

```json
{ "format": "sempere-insights-map/1", "device": "a1b2c3d4", "written": 1764727900000,
  "key": { "model": "nl-sentence", "lang": "en", "rev": 1, "input": 1 },
  "canaries": { "set": 1, "enc": "f16le-base64", "v": ["...", "..."] },
  "mean": "...",
  "clusters": [ { "id": 7, "parent": 2, "label": ["damping ratio", "resonance", "vibration"],
                  "centroid": "...", "members": ["6f1c2b9e-...", "..."] } ],
  "layout": { "6f1c2b9e-...": [0.412, -0.118] },
  "built": { "notes": 698, "hashes": "<SHA-256 over sorted noteId:emb.hash>" } }
```

Vectors are Float16 base64. Clusters form a two-level hierarchy (Louvain's levels), mean-centered. A
rebuild runs when more than 10% of notes changed since `built`, or weekly, in the power window;
cluster ids are matched to the previous build by member overlap so labels and positions stay put. 700
notes: about 1 MB of vectors across sidecars, a map of about 100 KB.

**Canaries**, for what a version tag cannot see: same-revision numeric drift across chips. A device
that supports the pin embeds the 8 canary sentences (`set` 1, listed in format §16) with its own
`input`; **compatible** when model, language, revision and `input` match and every canary's cosine is
at least **0.999**. The map device also checks each device record's canaries, so status shows
per-device compatibility before anyone places a note.

- **Compatible:** the device uses the synced vectors, edges and map. A note the map device has not
  embedded yet is embedded locally (cache only, never the vault) and **placed**: nearest centroid per
  level, position at the mean of its 3 nearest neighbours plus a small id-hashed offset; dashed
  outline, "Placed on this device; joins the map at its next rebuild"; related notes at once. The
  local vector is dropped when the map device's arrives.
- **Incompatible** (supports the pin but fails the canaries): one local vector set and local map
  (about 4 minutes for 700 notes), said in status, never mixed; back to the shared set when a later
  map passes. A vector reader, and the Linux CLI, use the synced set without a check.
- The map device checks its own stored canaries at launch; a failure re-embeds and rebuilds first.

## 4. Core library (Linux-tested)

`SempereInsights` (Foundation only, Linux, in `check-portability.sh`) holds the pipeline; the codec
`Sources/Sempere/InsightsFile.swift` sits beside `PublishedSummaries.swift`. `SempereInsightsApple`
(under `Sources/`, every file `#if canImport(FoundationModels)` / `NaturalLanguage`, as
`SempereSpeech` does; `@Generable` only inside it) holds the two real providers and is the only
target that imports them.

Two protocols: `ModelProvider` (identity = model, os, prompt; availability; 8192-token context [M];
`extract`, `merge`, `summarize`) and `EmbeddingProvider` (`supportedRevisions`, `embed(text, lang,
revision)`, its key). Fakes: `FakeModelProvider` (scripted; injects OCR typos, invented terms, failures, overflow) and
`FakeEmbeddingProvider` (hashed bag of words, so related notes get related vectors).

Pipeline, each a pure function with tests:

1. **Chunking.** chars / 3.5 tokens; single call up to ~330 words, else ~450-word chunks at
   paragraph then sentence boundaries plus a merge call [M: 1247 words in 3 chunks]. On a
   context-overflow error, halve and retry once.
2. **Normalization** (the biggest quality lever [M]): NFKC, lowercase, unify hyphen/space/underscore,
   strip punctuation, a small singularize/lemmatize rule set plus an English irregular table, drop
   symbol-only terms (`zeta`, `F0 sin(w t)`), dedupe, cap 10 keywords and 5 concepts.
3. **Stoplist and IDF.** Built-in generic stoplist plus any term in more than 50% of notes; TF-IDF
   over the vault's keyword documents; the reader recomputes IDF on its own corpus.
4. **Typo merge** against the vault's recognized-word frequencies: edit distance 1 (length <= 7) or
   2, only to a candidate at least 5x more frequent (`kinernatics` to `kinematics`).
5. **Summary fact check.** Checkable tokens (mid-sentence capitals, numbers with units, symbols,
   formula fragments, content nouns) must appear in the source after normalization and typo merge;
   a sentence with an unsupported one is dropped (`gen.dropped`). Over 40% dropped or empty: no
   summary, keywords only. At most 4 sentences / 600 characters, cut in code [M: length ignored].
   No `course` field [M: unreliable].
6. **Related-notes graph** (on each reader, from the compatible set of §3.8):
   - Embedding input: the note text with markers, bullets and equation lines stripped (D11); notes
     over 1000 words embed per chunk and average.
   - Mean-center and renormalize [M: compressed cosines]; hub damping by CSLS,
     `s(i,j) = 2 cos(i,j) - r_i - r_j`, `r_x` the mean cosine to x's 10 nearest neighbours [M: d17
     hub]; compilations (over 3x median length) weighted 0.8.
   - Keyword overlap: IDF-weighted Jaccard over normalized content tokens [M: AUC 0.80, top-3 1.00].
   - Score `0.6 z(csls) + 0.4 z(kw)`; keep an edge above a per-vault knee threshold with a floor, at
     most 8 per note, mutual-top-12 only, so an unrelated note stays unlinked [M: sourdough].
   - Each edge says why: top 3 shared keywords, or "similar wording".
   - No vectors at all (no map yet and no provider): keyword overlap alone.
7. **Clustering** (the map device, or an incompatible reader's local map). Louvain with sorted node order, fixed resolution, ties by lowest id; clusters
   under 3 notes merge into "Other"; two levels kept; label = top 3 terms by in-cluster over out-of-cluster IDF weight.
8. **Layout.** Fruchterman-Reingold, 300 iterations, initial positions from a hash of the note id,
   rounded to 1e-3, clusters on ring slots by id, warm-started from the previous build. Placement of
   a new note (§3.8) is a pure function too. Tests compare macOS and Linux with 1e-3 tolerance.
9. **Topic summaries.** Scope = a notebook or a tag with at least 3 summarized notes; up to 25 member
   summaries single shot [M: better and cheaper than map-reduce], above that per-cluster passes then
   one over those; at most 6 sentences; fact check as in 5 against members' summaries and keywords
   [M: "wave behavior"]; labeled "generated".
10. **Scheduling policy** (pure): notes, files, clock, capabilities, settings in; next work items and
    why out, including map-device claims and rebuilds. The app on every platform and the CLI call it.

## 5. Embedding consistency

All rules are in §3.8: one compatible set per reader (the map device's vectors at the pinned
revision, plus locally placed ones; or a wholly local set), never mixed; edges are computed
on each reader with deterministic code, so compatible devices agree.

## 6. UI (logic in core, SwiftUI is glue)

1. **Note info panel (all devices):** summary ("Generated on <device name>", date), keyword chips (tap
   = search), "Related notes" with the why-line, a "stale" marker when the hash differs.
2. **Find (`NoteSearch`):** keywords, concepts and summary as a lower-weight field after page text,
   matched in normalized form; a hit says "matched in summary". "Dynamics last year" = "dynamics" plus
   the existing date filter (D6). Insights of deleted notes appear only in Recently Deleted.
3. **Related notes** in the panel and the library selection's context menu.
4. **Topic summary:** "Summary" on a notebook or tag shows the stored paragraph with a "Generated"
   badge and a "Check sources" list of current members; stale when the members' hash digest changed.
   Generating devices regenerate it in the background (at most once a day per scope); "Regenerate" on
   a generating device runs it now (one ~7 s call [M]). No cluster summaries in 1.2 (D8).
5. **Mind map (PR 3):** the map device's note-cluster map (nodes = notes, labeled cluster regions
   with the two-level hierarchy as zoom levels, edges = the related graph; pan, zoom, tap to open), not
   a keyword graph [M: hairball]. Locally placed notes have a dashed outline (§3.8); a device on its
   own local map says so in a banner. If PR 3 slips, 1.2 ships
   clusters as a grouped list and the map moves to 1.3 (D9).
6. **Settings:** one switch per vault, `Note Insights`, off by default (D4); a one-time offer card on
   a capable device ("Summarize and connect your notes, on your devices only. About an hour of
   charging for 500 notes."). Turning it off says it deletes the stored insights. The embedding-model
   pin and its upgrade offer, with the devices it leaves out, live here too (§3.8, D12).

**Banned by test.** `Tests/SempereInsightsTests/NoCloudTests.swift`, a Linux-safe source scan in CI:
- no file under `Sources/` or `Apps/` mentions `PrivateCloudComputeLanguageModel`, conforms to
  `LanguageModel`, or names `ChatGPT`, `openai`, `anthropic`, `gemini` (a maintained list);
- `FoundationModels` is imported only in `SempereInsightsApple`, whose only model is
  `SystemLanguageModel.default` (no adapters loaded);
- `SempereInsights` and `SempereInsightsApple` import no `Network`, `URLSession` or
  `FoundationNetworking` and do not depend on `SempereWebDAV` (with `release-check.sh`'s existing
  networking scan, which needs no change);
- no `CoreSpotlight`, `CSSearchableIndex` or `AppIntents` in either target.
- Smoke check (Mac, agent-run, skipped without the model): `nettop` on the `sempere insights update`
  process over a local fixture vault shows no non-loopback connection. This proves only that Sempere's
  own process makes none (inference runs in a system process); the guarantee is the scan plus
  `SystemLanguageModel.default` being Apple's on-device model.

**Threat model.** (a) Summaries and keywords are derived plaintext, encrypted with the same keys
as the notes and decrypted only where notes are. (b) The storage provider newly sees `insights/`:
which notes were processed, by which device, when, and file sizes. (c) Embeddings are lossy but not
provably non-invertible: the map device's vectors and the map are in the vault under the same
encryption, re-seal, tombstone, purge and old-key cleanup rules as the summaries (§3.3); locally
placed vectors stay in the sealed cache. (d) Model output is untrusted input: bounded, escaped,
never executed, never fed back as instructions; note text is marked as data in prompts, the output is
a `@Generable` schema, and the model gets no tools. (e) Removed devices, epochs, re-encryption and
deletion: §3.3 and §3.6. (f) History and restore: sidecars describe only the current text; a restore
changes the hash and regenerates; no insight is kept per version.

**At rest on a device.** The **insights cache** (§10.1 purpose `insights-cache`, magic `SMPG` ‖
`0x01`, Application Support): decoded sidecars, this device's placed or local vectors and any local map, sealed like the summary
cache of §10, so it persists across launches and is unreadable without the vault key; a new epoch
derives a new folder (vectors recomputed, sidecars re-read). Insights terms join the in-memory
`NoteSearchIndex` only; the §10 summary cache and §12 published summaries are unchanged; no
Spotlight donation. `docs/format.md` gets §16 Insights (note, map and topics files, key, JSON,
order, the map-device, device-record, pin (lowest common, manual moves) and canary rules with the
canary sentences, deletion rules, bounds), a §1 layout line, a §1.3 row, the cache in §10.1, and one §7.5 sentence ("`insights/` carries
its own `format`; it needs no `features` entry").

**Privacy policy** (`docs/appstore/privacy-policy.md` and `docs/privacy/index.html`, same new date),
under "On-device features":
> **Note insights** (optional, off by default) use Apple's on-device language model to write a short
> summary and keywords for each note, and Apple's on-device language framework to find related notes.
> They are made only on your devices (one without Apple Intelligence shows the others'), never use Private

## Decisions (reviewed 2026-11-09)

- **D1 `features` marker: none.** Old apps ignore and never delete `insights/` (checked in code), and
  §3.3's current-key reads, re-seal and delete-below-re-encryption close the old-home and deletion
  cases; a marker would only make pre-1.2 devices read-only.
- **D2 Storage: per-note, per-writing-device sidecar (summary, keywords, concepts; plus the vector
  from the map device), ordered by `written`;** the smallest sync cost with no cross-device conflict.
- **D3 Encryption: age to the current epoch's `v_e` with the §4 tag (label `insights`), read under the
  current key only.** The draft's premise was wrong: both options are per-epoch keys and neither
  "survives" an epoch change; age wins for stock-`age` recovery and sameness with `settings.age`, and
  survival comes from re-sealing (no model work).
- **D4 Default: off, with a one-time offer on capable devices.** Hours of first-run compute and a new
  kind of derived plaintext should be a choice.
- **D5 Embeddings: synced and comparable (changed by the owner, 2026-11-09).** One map device writes
  Float16 vectors in its note sidecars and a map file (two-level clusters, centroids, layout); readers
  check 8 canary sentences at cosine >= 0.999 (D12 pins the revision), then use the shared set and place their own new notes
  locally, or else build one local set and map and say so, never mixing. Map device: the
  `insights.mapDevice` setting, claimed first by macOS, 14-day takeover. Per-device vectors only
  would make related notes and maps disagree across devices.
- **D6 Natural-language dates: not in 1.2;** the existing date filter covers the owner's example.
- **D7 Transcripts: not in 1.2;** long and spoken; superseded by D14 (`text/1` carries them).
- **D8 Topic summaries: notebooks and tags, made in the background by generating devices, in one synced
  `topics.<device>` file per device;** devices without the model read them, and no HMAC-named per-scope files are
  needed. Cluster summaries are cut for 1.2 (scope creep; the shared map makes them possible later).
- **D9 Mind map: in 1.2 as PR 3, a note-cluster map, with the cut line to 1.3.** The owner asked for
  it and it only draws PR 1's map data.
- **D10 OS minor update: no regeneration;** hours of compute for output that barely changes.
- **D12 Embedding versions: the lowest common revision, upgrades by choice (from the owner,
  2026-11-09).** Embed at an explicit pinned revision, by default the lowest every recently seen
  device supports (device records). The pin never moves by itself; "Use the newer embedding model"
  (or moving down) is a confirmed choice that lists the devices left out, which become vector readers
  whose new notes stay pending until a supporting device embeds them. No transform, no dual-revision
  transition. Canaries stay for same-revision drift across chips.
- **D11 Embedding input: cleaned raw text.** Keywords already enter through the overlap term, and it
  works for notes without a summary. No A/B gate in PR 1; a later change bumps `key.input`, which the
  key treats as a new embedding: the map device re-embeds once, like an upgrade.

## Risks

- Quality on real handwriting is unmeasured [M]: fact check, typo merge, "Generated" labels, owner
  check 4.
- Compute: ~6 s per note [M]; a large vault takes nights on battery devices. macOS generates first;
  progress shown; tiers 0-1 meanwhile.
- `BGProcessingTask` runs at iOS's discretion; a vault with no macOS device is slow to fill.
- **Cross-chip agreement is unmeasured** (the simulator runs no embedder): owner check 0 before PR 1.
  If chips differ, devices that fail run local maps until the design is revisited.
- **After an upgrade, unsupported devices can't place new notes:** their new notes have no vectors
  (pending) until a supporting device syncs; the warning names them before the user confirms.
- **Apple may drop an old revision from new OSes:** the newest device then cannot run the pin and is
  a vector reader until the user upgrades; status says so.
- **Canaries can pass while other text drifts:** 8 varied sentences at 0.999 make it unlikely, not
  impossible [I]; check 0 also compares the corpus.
- **Absent map device** (new): the map stales (placements pile up) until the 14-day takeover; the
  owner can move it in Settings at once.
- **More synced derived data:** vectors add ~1.4 KB per note (about 1 MB for 700 notes); an upgrade
  rewrites every sidecar once.
- FM can change in a point release: `prompt`/`os` staleness makes it a recompute, never corruption;
  NLEmbedding changes arrive as revisions (pinned) or drift (canaries). The 8192-token window is a hard limit [M].
- Many small files on WebDAV/iCloud (one per note per writing device, usually one): only
  changed notes are written; per-device packs if this ever measures badly.
- Prompt injection from note text: no tools, a guided schema, validators, escaped output.
- Old-app home re-encryption leaves stale old-key sidecars until a 1.2 device syncs (§3.6).
- Graph tuning came from a 22-note synthetic corpus: thresholds are per-vault and adaptive, and
  `insights related --json` shows scores.

## 11. Revisions after the owner's review (2026-11-13)

**D13 One designated work device, by capability only (owner: "not macOS first").** The shared setting
`insights.workDevice` (replaces `insights.mapDevice`) names the device that generates summaries,
keywords and titles, embeds every note and builds the map. Any device where the models are available
may hold it; the platform never decides. Settings lists the capable devices (from device records) and
the user picks one; unset, the first capable device to turn Note Insights on claims it (§13.3's slot
merge settles a race). There is no automatic takeover: if the work device has written nothing for 14 days,
Settings and `status` say "work device not seen for 14 days" and offer "Use this device" (the user designates).
Summaries pause meanwhile. The role needs the pinned embedding revision; it generates only where Foundation Models
is available, and the picker labels a device without it "related notes and map only". CLI: `sempere insights
work-device [ID | --claim]`. Other capable devices do nothing unless the user also allows them
(`insights.compute = auto` on that device, default `never` when a work device is set), so work is not
duplicated. Power policy stays per platform but only decides *when* the designated device runs (on
power; on battery devices while charging, as `BGProcessingTask` with external power), never *who*.
The macOS-at-once / iOS-after-24-hours rules of §3.7 and §3.8 are removed.

**D14 Transcripts and voice-note titles in 1.2 (reverses D7).** `hashBasis` `text/1`, defined with transcripts (nothing shipped wrote a `text/1` without them, so there is no
`text/2`): the insight

## PR 1 notes (implementation, 2026-11-14)

Where the design left a choice open, or a point could not be built as written, PR 1 took the conservative option:

1. **Unset is not off.** Devices delete `insights/` only when `insights.enabled` is an explicit `false` at the top level
   of `settings.age` (format.md §16.6). With the key unset (every vault before 1.2, or a device that could not read the
   file) sync neither uploads nor deletes anything there. `insights.enabled` is vault-wide: a type block does not count.
   `sempere insights update` refuses (exit 1) while the feature is off, and `purge` writes the explicit `false`.
2. **No deletion beyond §16.6's list.** A device's own file that is only on the target is taken like any other (never
   deleted there), and a device that loses the work-device role writes a tombstone map (no `key`) instead of deleting
   its map file (§3.8 said "deletes"). Its old `emb` members stay until it rewrites those files; readers take `emb`
   and the map only from the current work device.
3. **The capture's time zone** is not recorded in a capture (format.md §11.2), so `{date}` and `{time}` come from the
   capture's default title (`Voice note YYYY-MM-DD HH:mm`, written in the capturing device's zone), else from the
   recording's start in UTC.
4. **Eligibility** ("the hash unchanged for 10 minutes") is approximated by the note's modified date being at least 10
   minutes old: the CLI keeps no per-device history of hashes. The app (PR 2) can track it per note.
5. **The fact check's "content nouns"** have no part-of-speech tagger on Linux: a content word is one of five letters or
   more outside a generic stoplist and a list of the words summaries use to talk about a note; numbers, mid-sentence
   capitals and formula symbols are always checked. On the first real-model run (agent Mac, 2026-11-14) summaries of
   technical notes kept most sentences, while summaries that name an inferred topic ("a recipe for bread" for a note
   that never says either word) were dropped to keywords only. The D16 run tunes the lists and the 40% rule.
6. **`InsightsStore` takes no `VaultFileLock`.** Each file has one writer per device and is replaced atomically; the CLI
   writes without the store lock as it does for other per-device files, and the app (PR 2) wraps its insights writes in
   the vault's write lock as it does `settings.age`.
7. **Deletion below a re-encryption on a target** happens when the sync pass reads the file (a new or changed copy, or
   one this device has not compared yet), not by a separate scan with a memo as for `summaries/`; the
   re-encryption's confirm step does not wait on insights (hints).
8. **`insights.compute`** defaults to `never`; with no work device set, the first capable device claims the role, so
   nothing waits on the default. Devices that are not the work device never write `emb` (placement stays local).
9. **Topic summaries** (behind the D19 cut line for the app) are made by `update` when due (at least 3 summarized
   members, the members' digest or the model changed, at most once a day) and by `insights topic --generate`.
10. **Settings.** The five keys are additive to `$schemaVersion` 1 (`registry-v1.json` gains them; no migration). The
    app's settings bridge treats them as model keys (never stored per device, never seeded from a device), and
    `testCatalogMatchesWhereTheAppShowsEachSetting` exempts them until PR 2 adds Settings ▸ Note Insights.
11. **Old readers.** The committed old-reader scenario runs this PR's code with the setting unset, which takes the same
    paths main takes (no insights handling); main's own binary was also run once against a vault holding `insights/`
    (open, verify, sync to a folder target, push-only with `--delete-extraneous`, backup, merge-copy) and left it
    byte for byte (PR description, "Tests run").
12. **`LocalChanges`** does not yet report arrived insights files; the app's reload of them comes with PR 2.
