# Linux CLI: a cut WebDAV upload stalls until the idle timeout (1.2)

Status: plan, 2026-11-13. Paths are relative to the repository root. This was written by reading code only: no Linux
run was possible, so the cause is not located and section 3 starts with the run that locates it.

## 1. Problem

On Linux, a WebDAV upload whose connection is reset in the middle of the request body is not noticed until the
transport's idle timeout, 60 seconds by default. On macOS the same cut fails in about 2 seconds. There is no data risk
(write-once names and the temporary-name-then-move upload, `SyncEngine.placeWriteOnce`, keep a cut file from landing),
but a Linux CLI sync loses a minute per cut file. `ReencryptOverWsgidavFaultProxyTests` sat about 60 seconds per cut (six
cuts took that test 370 seconds on Linux, 2 seconds on macOS) and now runs with `URLSessionTransport(timeout: 5)` to hide it
(`Tests/SempereWebDAVTests/ReencryptOverWsgidavFaultProxyTests.swift:37`, comment above it). The entry in the
maintainer's TODO says only "Foundation/URLSession or our client".

## 2. What the code does today

- One transport, `URLSessionTransport` (`Sources/SempereWebDAV/Transport.swift`), on `URLSession` (on Linux through
  `FoundationNetworking`, which is libcurl underneath). Two ephemeral sessions: one for in-memory bodies
  (`timeoutIntervalForResource` 600 s) and one for streamed files (`7 * 24 * 3600`), both with
  `timeoutIntervalForRequest = timeout` (default 60, line 145-151), no cache, no cookies, one connection per transfer
  (`httpMaximumConnectionsPerHost = TransferPool.maxWidth`).
- `send` (line 169) makes a `dataTask` with `httpBody`, or an `uploadTask(fromFile:)`, registers a `Pending`, resumes it
  and waits on a semaphore (`pending.done`), in a 250 ms poll only when the request has an `interrupt`
  (lines 187-198). The task's end comes from the delegate's `didCompleteWithError`. Our client adds no timer, no retry and
  no keep-alive handling of its own; it neither implements `urlSession(_:task:didSendBodyData:...)` nor reads the
  task's progress. So the 60 seconds is `timeoutIntervalForRequest` firing, which means the task saw no I/O error and
  no progress: the reset did not reach the task as an error.
- The fault is `scripts/dav-fault-proxy.py`'s rule `reset` with `direction: request`: it reads `afterBytes` of the body and
  closes the client's socket with `SO_LINGER 0` (`rst()`, lines 152-160), a TCP RST (lines 259-262).
- Idle-timeout behavior is tested for a stalled server and a stalled streamed upload
  (`WsgidavFaultProxyTests.testStalledServerTimesOut`, `TransportChallengeTests.testStalledStreamedUploadTimesOut`), both on
  a server that stops reading, not one that resets.

## 3. Where the stall comes from: candidates and the run that decides

Not verified. In order of how cheaply each is checked:

1. **The harness's reset is late on Linux.** `rst()` calls `self.connection.close()` on the handler's socket after setting
   `SO_LINGER`. CPython closes the descriptor only when the last `makefile` reference goes, and `rfile` holds one until
   the handler's `finish()`; the RST then goes out when the handler returns. That should be prompt (the handler returns at
   once), but it is the first thing to rule out: log the monotonic time of the cut and of `finish()` in the proxy, and
   check with `ss -tn` or a packet capture that the RST leaves when expected. If the cut is late, the fix is in the proxy
   (`socket.shutdown`/`detach` then close), not the client.
2. **libcurl or corelibs does not turn the RST into a task error while the body is being sent.** Run the same cut with
   an in-process server (the tests' `SlowHTTPServer` in `Tests/SempereWebDAVTests/TransportChallengeTests.swift` is the
   pattern), one that reads N bytes and closes with `SO_LINGER 0`, for each body mode: `httpBody` (a revision), `fromFile`
   (a blob) and a body larger than the socket buffers (so the client is still writing when the RST arrives) and smaller
   (so the client has finished writing and waits for a response). Time each and record the error. This tells whether the
   stall is in the write path, the read path or neither.
3. **A reused connection and a retry.** The sessions keep connections alive; a reset of a reused connection may lead the
   stack to retry on a new one, and the retry meets the proxy's next rule. Compare a first request on a fresh transport with
   one after an earlier request.
4. **The idle timer is not what ends it.** If a libcurl verbose log (the corelibs sources have a debug switch; confirm its
   name in the toolchain used by `scripts/test-linux.sh`) shows the connection was closed at once but the task completed
   only at 60 seconds, the completion callback is late (a corelibs bug in how it reports a failed upload), and a client-side
   watchdog is the only fix.

The diagnostic is a Linux-run test target (`TransportResetTests`, in `SempereWebDAVTests`, no wsgidav needed) that prints
the table above, plus the proxy's timing log. It is run locally first (`scripts/test-linux.sh`, Docker on the Mac) and its
results go in the PR description; the test and the fix land in the same, single PR. The harness candidate (1) is ruled
out first. Its output decides which fix below applies.

## 4. Fix

If the cause is the harness (1): fix the proxy, restore the default timeout in `ReencryptOverWsgidavFaultProxyTests`, done.

If the cause is in URLSession on Linux (2 to 4): a **progress watchdog** in `URLSessionTransport`, active on Linux (and
available to tests on every platform through an initializer parameter), because Apple's stack already reports the reset.

- A `Pending` records `lastActivity` (a monotonic clock) and the body's progress: `urlSession(_:task:didSendBodyData:
  totalBytesSent:totalBytesExpectedToSend:)` and `didReceive data` both update it, and `didReceive response` marks the
  body as finished. (Whether corelibs calls `didSendBodyData` for `httpBody` and `fromFile` uploads is unverified; the
  first PR's test checks it. If it does not, the watchdog falls back to polling `task.countOfBytesSent`, which corelibs
  does maintain.)
- `send` always polls (the 250 ms loop now runs for every request, not only those with an `interrupt`): when a request
  has a body, the body is not fully sent (`countOfBytesSent < countOfBytesExpectedToSend`) and no byte moved for
  `bodyStallTimeout` (default 15 seconds, Linux; infinity elsewhere), it cancels the task and throws
  `WebDAVError.offline("upload stalled: no bytes sent for 15 s")`, which the sync treats like any other lost connection
  (`Transport.offlineCodes`, `WebDAVError.offline`): the run records the failure and the next run retries the file
  from its temporary name.
- A body under the socket send buffer (a few KB revision against Linux's MB-scale autotuned buffer) reaches
  `countOfBytesSent == expected` at once, so the body-phase condition above is never true for it, and the cut revision
  files of `ReencryptOverWsgidavFaultProxyTests` are exactly that size. If the diagnostic shows the stall in the wait for
  the response, the fix also covers that phase: a Linux-only first-response-byte timeout of 15 seconds (`SEMPERE_WEBDAV_BODY_STALL`
  sets both) for bodies of 1 MiB or less, since a small PUT is answered fast.
- Large PUTs keep the idle timeout after the body is fully sent: the server may take a long time to answer (it hashes,
  syncs, moves), and that wait is the idle timeout's, as today. It does not apply to downloads (the existing idle
  timeout and the sync's run bound with `interrupt` handle them).
- 15 seconds is a floor for a link that moves nothing at all for that long mid-body; a slow link that still moves bytes
  never trips it. A user on a link that really stalls for 15 seconds in the middle of a large blob gets a retry that
  re-sends the blob (a PUT cannot resume), which costs more than the stall. If that matters, the default scales with the
  body: `max(15 s, 2 s per MiB)`, still resetting on any progress. The recommendation is the flat 15 seconds, adjustable by
  the `SEMPERE_WEBDAV_BODY_STALL` environment variable for the CLI, and not exposed in the app (which is not affected: Apple's
  stack reports the reset).
- The checks stay where they are: the idle timeout (60 seconds) is the backstop, `interrupt` still stops a run on cancel
  and its time bound.

If the cause is a late completion callback (4), the same watchdog applies; it is then also the fix for the stall of a
download whose connection is reset mid-body, which should be tested the same way.

## 5. Tests

- The first PR's `TransportResetTests` (Linux, no external server): the table of section 3, for `httpBody`, `fromFile`,
  a small and a large body, a fresh and a reused connection. On macOS it runs too and shows the 2-second baseline.
- With the fix, on Linux, with the fault proxy and wsgidav (`scripts/test-webdav.sh`, the job that already runs it):
  - a cut upload (`reset`, `direction: request`, `afterBytes` inside the body) on a transport with the default timeout
    (60 s) and `bodyStallTimeout` 3 s fails in under 10 s with `.offline`, and the next run converges
    (`WsgidavFaultProxyTests`, beside `testStalledServerTimesOut`);
  - the same cut for a streamed blob (`fromFile`);
  - a throttled upload (`bytesPerSecond` low enough to take longer than `bodyStallTimeout` in total but never idle for
    that long) completes: the watchdog must not fire on slow progress;
  - a server that reads the whole body and then waits longer than `bodyStallTimeout` before answering (the proxy's
    `stall` action) is not cut by the watchdog (the idle timeout's job);
  - a server that stops reading after N bytes (the existing `testStalledStreamedUploadTimesOut` shape) now ends at
    `bodyStallTimeout`, not at the idle timeout.
- `ReencryptOverWsgidavFaultProxyTests` loses its `timeout: 5` and goes back to the default transport, which is the proof
  the stall is gone: its six cuts must take well under 60 seconds in all, with a generous timing bound in the test
  (`XCTAssertLessThan`) so the 370 second regression shows as a failure without a timing flake.
- A small PUT cut after the body is fully sent and a small PUT whose response never comes (the proxy's `stall`) both end at
  the first-response-byte timeout; a large PUT's slow response is not cut.
- The portable pieces (the `Pending` clock and the decision "stalled or not" as a pure function of times and byte counts)
  get plain unit tests that need no network.

## 6. Open questions, with recommended answers

1. **Fix the client, or is it the harness?** Unknown until the diagnostic runs; section 3 orders the checks, and the harness
   comes first because it costs a log line.
2. **Is a flat 15 seconds right?** Yes, adjustable by environment variable for the CLI; reset by any progress.
3. **Apply it on Apple platforms?** No: the stack reports resets there (about 2 seconds in the same test), and a watchdog
   would only add a way to cancel a slow upload. The parameter exists so a test can exercise it there.
4. **Should the test timeout of 5 s stay as well?** No; remove it once the watchdog is in, so the test proves the fix.
