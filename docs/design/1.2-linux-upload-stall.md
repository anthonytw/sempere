# Linux CLI: a cut WebDAV upload stalls until the idle timeout (1.2)

Status: plan, 2026-11-13; fixed by PR #48 (section 4). Paths are relative to the repository root. This was written by reading code only: no Linux
run was possible, so the cause is not located and section 3 starts with the run that locates it.

## 1. Problem

On Linux, a WebDAV upload whose connection is reset in the middle of the request body is not noticed until the
transport's idle timeout, 60 seconds by default. On macOS the same cut fails in about 2 seconds. There is no data risk
(write-once names and the temporary-name-then-move upload, `SyncEngine.placeWriteOnce`, keep a cut file from landing),
but a Linux CLI sync loses a minute per cut file. `ReencryptOverWsgidavFaultProxyTests` sat about 60 seconds per cut (six
cuts took that test 370 seconds on Linux, 2 seconds on macOS) and now runs with `URLSessionTransport(timeout: 5)` to hide it
(`Tests/SempereWebDAVTests/ReencryptOverWsgidavFaultProxyTests.swift:37`, comment above it). The entry in the
maintainer's TODO says only "Foundation/URLSession or our client".

## 2. What the code does today

- One transport, `URLSessionTransport` (`Sources/SempereWebDAV/Transport.swift`), on `URLSession` (on Linux through
  `FoundationNetworking`, which is libcurl underneath). Two ephemeral sessions: one for in-memory bodies
  (`timeoutIntervalForResource` 600 s) and one for streamed files (`7 * 24 * 3600`), both with
  `timeoutIntervalForRequest = timeout` (default 60, line 145-151), no cache, no cookies, one connection per transfer
  (`httpMaximumConnectionsPerHost = TransferPool.maxWidth`).
- `send` (line 169) makes a `dataTask` with `httpBody`, or an `uploadTask(fromFile:)`, registers a `Pending`, resumes it
  and waits on a semaphore (`pending.done`), in a 250 ms poll only when the request has an `interrupt`
  (lines 187-198). The task's end comes from the delegate's `didCompleteWithError`. Our client adds no timer, no retry and
  no keep-alive handling of its own; it neither implements `urlSession(_:task:didSendBodyData:...)` nor reads the
  task's progress. So the 60 seconds is `timeoutIntervalForRequest` firing, which means the task saw no I/O error and
  no progress: the reset did not reach the task as an error.
- The fault is `scripts/dav-fault-proxy.py`'s rule `reset` with `direction: request`: it reads `afterBytes` of the body and
  closes the client's socket with `SO_LINGER 0` (`rst()`, lines 152-160), a TCP RST (lines 259-262).
- Idle-timeout behavior is tested for a stalled server and a stalled streamed upload
  (`WsgidavFaultProxyTests.testStalledServerTimesOut`, `TransportChallengeTests.testStalledStreamedUploadTimesOut`), both on
  a server that stops reading, not one that resets.

## 3. Where the stall comes from: candidates and the run that decides

Not verified. In order of how cheaply each is checked:

1. **The harness's reset is late on Linux.** `rst()` calls `self.connection.close()` on the handler's socket after setting
   `SO_LINGER`. CPython closes the descriptor only when the last `makefile` reference goes, and `rfile` holds one until
   the handler's `finish()`; the RST then goes out when the handler returns. That should be prompt (the handler returns at
   once), but it is the first thing to rule out: log the monotonic time of the cut and of `finish()` in the proxy, and
   check with `ss -tn` or a packet capture that the RST leaves when expected. If the cut is late, the fix is in the proxy
   (`socket.shutdown`/`detach` then close), not the client.
2. **libcurl or corelibs does not turn the RST into a task error while the body is being sent.** Run the same cut with
   an in-process server (the tests' `SlowHTTPServer` in `Tests/SempereWebDAVTests/TransportChallengeTests.swift` is the
   pattern), one that reads N bytes and closes with `SO_LINGER 0`, for each body mode: `httpBody` (a revision), `fromFile`
   (a blob) and a body larger than the socket buffers (so the client is still writing when the RST arrives) and smaller
   (so the client has finished writing and waits for a response). Time each and record the error. This tells whether the
   stall is in the write path, the read path or neither.
3. **A reused connection and a retry.** The sessions keep connections alive; a reset of a reused connection may lead the
   stack to retry on a new one, and the retry meets the proxy's next rule. Compare a first request on a fresh transport with
   one after an earlier request.
4. **The idle timer is not what ends it.** If a libcurl verbose log (the corelibs sources have a debug switch; confirm its
   name in the toolchain used by `scripts/test-linux.sh`) shows the connection was closed at once but the task completed
   only at 60 seconds, the completion callback is late (a corelibs bug in how it reports a failed upload), and a client-side
   watchdog is the only fix.

The diagnostic is a Linux-run test target (`TransportResetTests`, in `SempereWebDAVTests`, no wsgidav needed) that prints
the table above, plus the proxy's timing log. It is run locally first (`scripts/test-linux.sh`, Docker on the Mac) and its
results go in the PR description; the test and the fix land in the same, single PR. The harness candidate (1) is ruled
out first. Its output decides which fix below applies.

## 4. Fix (as built)

Status of the investigation, 2026-11-14: the cause is located (PR #48), and the first fix in this document (a progress
watchdog plus a first-response-byte timeout) was replaced after review by a fix of the cause. The text of section 3 above
stays as the plan that found it.

**Cause.** It is neither the proxy (curl through it fails in 8 ms) nor a fresh connection (`TransportResetTests`: 0.0 s for
every body mode and size). It is a cut PUT on a **reused (kept-alive) connection** under swift-corelibs-foundation:

1. libcurl sees the reset on the reused connection and retries the request on a new one, rewinding the body through
   `CURLOPT_SEEKFUNCTION`.
2. corelibs' seek callback (`NativeProtocol.seekInputStream(to:)`) asks the task delegate for
   `urlSession(_:task:needNewBodyStream:)`. We did not implement it, so the default answers nil and corelibs reports the
   rewind as done without rewinding anything. (`default: fatalError()` there means it can rewind only a `httpBodyStream`
   body, never `httpBody` or an `uploadTask(fromFile:)` source.)
3. The `httpBody` or file source was already drained, so the retry sends the headers with `Content-Length: N` and no body
   bytes, and the server waits for the body until the idle timeout (60 s).

Steps 1 to 3 were read in the corelibs source by the reviewer of PR #48; the measurements above agree: a cut on a reused
connection took the whole idle timeout, the next one (fresh connection) 0.0 s, and raw libcurl logs the retry.

**Fix, Linux only** (`#if canImport(FoundationNetworking)`, `URLSessionTransport.send`): a **PUT** body is sent as
`URLRequest.httpBodyStream` (`InputStream(data:)`, or `InputStream(url:)` for a file) on a `dataTask`, and the session
delegate implements `urlSession(_:task:needNewBodyStream:)`, which hands out a new stream of the same body. libcurl's
retry then re-sends the body. Apple platforms are unchanged (no stream body; they report the reset).

What the stream costs, found by running it (the first version of PR #48 streamed every body with an explicit
`Content-Length`, and `testPartialCopyLifecycle` then failed about one run in three):

- corelibs has no length for a stream (`getBodyLength()` is nil, so `requestBodyLength` is `.unknown`) and sends it
  **chunked whatever the headers say**. A `Content-Length` of ours is not a hint, it rides along beside
  `Transfer-Encoding: chunked` (captured on the wire), so the header is dropped for a streamed PUT. A chunked PUT is a real compatibility risk, not a theoretical one:
  - wsgidav consumes the chunks (CI runs it), but servers differ. Some answer 411 Length Required or 501 to a chunked
    request body. Others are worse: Nextcloud and ownCloud behind Apache with PHP-FPM can answer 201 and store an empty or
    short file for a chunked PUT, unless the client announces the length in `X-Expected-Entity-Length` (the header
    Finder and Cyberduck send for the same reason).
  - So every streamed PUT carries `X-Expected-Entity-Length: <exact byte count>`, and a 411 or 501 to a chunked PUT is
    retried once with a fixed-length body (`Content-Length`, no stream) and remembered for the transport: its later PUTs
    are fixed-length from the start (`URLSessionTransport.putsAreFixedLength`). A fixed-length PUT keeps today's
    behavior, including the unrewound retry on a dead connection.
  - What still catches a truncated file a server stored anyway: for a revision or another write-once file both sides
    list, `SyncEngine.repairCutFile` / `repairCutRevision` replace a copy whose listed size is below the local one and is a
    prefix of it, but only on a **later** run, and only when the server lists sizes. A blob has no uploader-side repair: a
    downloading device rejects it by listed size and by hash (`BlobSync`), and the uploader keeps believing it uploaded
    it. A server that stores a short chunked PUT without announcing it (and without the header being honored) is
    therefore a **remaining limit** for blobs: they are detected at the reader, not repaired at the writer.
  - `needNewBodyStream` is the only rewind corelibs offers, which is why the stream is kept.
- wsgidav (cheroot) does **not** consume a chunked **PROPFIND** body: it answers 207 from the first chunk and then reads
  the rest of the chunk framing as the next request line, which answers `400 Malformed Request-Line` on the kept-alive
  connection, and the next request on it fails ("PROPFIND ... failed: HTTP 400"). So only PUT is streamed; PROPFIND and any
  other request with a body keep a fixed-length body, and a libcurl retry of one of those on a connection that died is
  still not rewound (a tiny body; the idle timeout is the backstop, as before).
- Tried and dropped: a connection per request with a body (`Connection: close` in sessions of their own). libcurl did not
  close after the request (the proxy log shows a second request on the same connection), it still hung on a retried
  `Content-Length` with no body, and the connection churn saturated the 10 workers of the wsgidav behind the fault proxy
  (`testRequestCountsOnASlowLink`: 242 s).

Also in the same change:

- A connection reset that corelibs reports under a code outside `offlineCodes` ("Recv failure: Connection reset by peer",
  "Send failure: ...", "Broken pipe") is classified `.offline` (`URLSessionTransport.isConnectionReset`), so the sync
  treats a cut upload like any lost connection.
- After `cancel()` (the `interrupt` path) `send` waits at most `cancelGrace` (30 s) for the completion, so a completion
  that never comes cannot hang the CLI.

**Not built, and why.** The 60 s idle timeout stays the backstop, as on macOS; there is no upload watchdog. The first
version had a 15 s body-progress watchdog and a first-response-byte limit for bodies of 1 MiB or less. The second rule
was rejected: a small body counts as sent as soon as it is in the socket buffer, so on a slow uplink (a body near 1 MiB
below about 70 KB/s) it fails on every attempt and the file never syncs; a rate low enough to be safe makes the limit
longer than the idle timeout. A peer that stops reading mid-body is not this bug, and the idle timeout already handles it
on both platforms. If a stream body turned out not to work on corelibs, the fallback would be the watchdog, not the
default.

## 5. Tests (as built)

- `TransportResetTests` (in-process server, no wsgidav): `testABodyIsFramedOnce` (a PUT is length-framed or chunked,
  never both; PROPFIND keeps its length); the table of section 3 (`httpBody` and `fromFile`; 2 KB, 64 KB,
  2 MiB and 8 MiB; cut after 100 B to 100 KB): every cut fails in under 10 s and is classified `.offline`; an `interrupt`
  cancels an upload the server stopped reading, for both body modes, within seconds.
- `WsgidavCutUploadTests` (proxy and wsgidav, one transport so the connection is reused, default 60 s idle timeout): a cut
  small PUT, a cut 2 MiB PUT (it fits in the socket buffers, the case a progress watchdog misses) and a cut streamed 4 MiB
  file each fail in under 10 s with `.offline`, and the next run converges; a PUT cut once on a reused connection ends at once,
  and where libcurl retries it (a race with the body's last writes) the retry carries the whole body; a throttled 8 MB upload completes.
- `ReencryptOverWsgidavFaultProxyTests` lost its `timeout: 5` and asserts its cut sync takes under 30 s (370 s before the
  fix on Linux, about 10 s after).

## 6. Decisions

1. **Harness or client?** Neither the harness nor a fresh connection: corelibs' body rewind on libcurl's retry (section 4).
2. **Apple platforms?** Unchanged: the stack reports resets there and never retries these bodies through the delegate.
3. **A progress watchdog?** Not built (section 4, "Not built, and why").
