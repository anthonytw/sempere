# Screenshots for 1.2: App Store, website and dark twins

Status: design, 2026-11-13. Paths are relative to the repository root unless they say "site". The site is the project
website's repository (`sempere-site`); this design only describes what changes there, and the site PR is made in that
repository. Nothing here is uploaded by an agent: the maintainer uploads App Store images
(`docs/appstore/screenshots.md`).

## 1. Goal

1. New App Store screenshots that show Undo and Redo (1.1) and whatever 1.2 adds on the note screen.
2. Website screenshots for the Watch page and for the nearby join request.
3. Dark-mode twins of the website's screenshots, shown when the site is in dark mode, with only one of the pair
   loaded.

Non-goals: dark App Store shots (the store takes one set per size; a dark set is a later choice), real notes (a demo
never holds real notes, CLAUDE.md), new devices.

  `PKCanvasView`).
- The store set is `01-write` to `06-unlock`, written before 1.1 (the Undo and Redo buttons, `undoButton` and
  `redoButton`, `Apps/Sempere/SempereApp/NoteCanvasView.swift:737`, are in the note toolbar; today's shots show them
  disabled, if the bar shows them at all in the demo's annotate mode: not checked).

## 3. Design

### 3.1 App Store: a set with Undo and Redo

- The shot gets its state from the test, as the guide shots do (`DocsScreenshotTests` already taps its way), not from a
  launch variable: before shooting `01-write` and `02-sketch`, `ScreenshotTests` draws two short strokes in an empty
  part of the page with a finger drag (the way `IPadCanvasUITests` drives the canvas) and taps Undo once. Undo and Redo
  are then both enabled, so the shot says what the buttons do, and one stroke remains, placed to read as an underline
  under the heading. An alternative that leaves the page untouched is the item move that
  `IPadCanvasUITests.testTheToolbarsUndoAndRedoButtonsUndoAnItemMove` uses (`SEMPERE_DEMO_ITEMS`, a drag of the selected
  image), which changes what the page shows; the PR picks the one that looks better and says which. The iPhone shots
  take the same steps in the compact palette, which has its own Undo and Redo (`DrawingPaletteView`).
- Order of the set (the first three show in search results): `01-write` and `02-sketch` carry the Undo and Redo state,
  then `03-notes`, `04-tags`, `05-paper`, `06-unlock` as today. Recommendation: fold the state into those two shots and
  add no seventh, so the first three carry the feature and the listing stays at six. Note Insights adds one more store
  shot (related notes) in its own PR, not here.
- The Mac set keeps its single window layout; Undo and Redo are in its Edit menu, which a window shot does not show.
- Sizes and the size check in the script are unchanged. `docs/appstore/screenshots.md` "The shots" is updated.

### 3.2 Website: Watch and the nearby join request

- **Watch**: a new target in `scripts/screenshots.sh`, `docs-watch`, running a `WatchScreenshotTests` class in
  `SempereWatchUITests` (`Apps/Sempere/SempereWatchUITests`, which already drives every state on a fake recorder:
  `scripts/app.sh test-watch-ui`) on the newest watchOS simulator (`scripts/app.sh` already picks one for the watch
  runs). It saves the screens the Watch page describes: ready to record, recording, saved, and the complication or widget
  if the page shows it. The simulator's screenshot of the watch screen (a PNG at the watch's native size) goes to
  `build/screenshots/docs-watch/`. Size check in the script: the native size of the chosen watch, whatever it is, taken
  from the first PNG and required of the rest.
- **Nearby join request**: a DEBUG launch variable `SEMPERE_DEMO_NEARBY_JOIN=1` makes the demo's home device (with
  `SEMPERE_DEMO_DEVICE_KEY` so it is home) seed `nearbyRequests` with one synthetic `JoinRequest` (throwaway keys, the
  name "Demo iPhone", kind `iphone`) and open Add Device, so the sheet shows the request row marked Nearby. After the
  join-confirm PR (1.2-join-confirm.md) the row also shows its six words and "They Match"; the shot is taken after that
  PR, so the website never shows the old typed-only sheet. A second shot is the new device's join screen waiting, with
  its six words and the line that says it found the device nearby (`JoinDeviceView`, a `waiting` stage). Both iPad, in
  the guide's usual size.
- The raw shots are `docs-ipad/docs-nearby-join.png`, `docs-ipad/docs-join-waiting.png`, `docs-watch/*.png`; site's
  `media.mjs` gets the jobs, and the two pages gain `<Shot>`s.

### 3.3 Website dark twins

The page shows one image of each pair, chosen by the same selectors the stylesheet already uses for everything
else, so the theme toggle and the system setting both work, and only the visible one is fetched.

**Site, `media.mjs`:** for each shot, a raw dark capture `…-dark.png` (a second run of the same tests with the
simulator in dark appearance, below) becomes `public/media/<name>-dark.webp` and a `<name>-dark` entry in
`media.json`. A job whose dark capture is missing is skipped like any other absent capture (the light image stays).

**Site, a new `ThemedImage.astro`**, used by `Shot.astro` and by `index.astro` in place of its bare `<img>`:

```astro
---
// name: the light image's name in public/media; the dark twin is `${name}-dark` when its file exists.
const dark = existsSync(`public/media/${name}-dark.webp`) && dims[`${name}-dark`];
---
<img class="shot-light" src={`/media/${name}.webp`} alt={alt} width={w} height={h} loading="lazy" decoding="async" />
{dark && <img class="shot-dark" src={`/media/${name}-dark.webp`} alt="" aria-hidden="true" width={dw} height={dh}
               loading="lazy" decoding="async" />}
```

**Site, `global.css`:**

```css
.shot-dark { display: none; }
:root[data-theme="dark"] .shot-light { display: none; }
:root[data-theme="dark"] .shot-dark { display: block; }
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) .shot-light { display: none; }
  :root:not([data-theme="light"]) .shot-dark { display: block; }
}
```

Why two `<img>` and not `<picture>` with `media="(prefers-color-scheme: dark)"`: a `<picture>` source follows only the
system setting and would ignore the site's own toggle (the `data-theme` attribute). Why only one loads: a `loading="lazy"`
image that is `display: none` is never rendered, so the browser has no reason to fetch it; the hidden twin loads only
if the reader switches theme and scrolls to it. The twin has an empty `alt` and `aria-hidden` so a screen reader hears one
image. Width and height are both set from `media.json`, so there is no layout shift when the theme changes and the two
sizes are the same. If a pair's sizes ever differ, `ThemedImage` uses the light image's for both and the build warns.
The hero video (`hero-ipad.mp4`, `hero-ipad.webm`) and its poster keep one version: a dark video doubles a large download
for one section, and the hero sits on a card that keeps its own background in both themes.

**This repository, capture in dark appearance:**

- `scripts/screenshots.sh` takes `SEMPERE_SHOTS_APPEARANCE=dark` (default `light`): it runs
  `xcrun simctl ui "$sim" appearance dark` instead of light, writes into `build/screenshots/<name>-dark/`, and passes the
  setting to the tests with `TEST_RUNNER_SEMPERE_SHOTS_APPEARANCE`. The status bar override is the same.
- `DemoLaunch.forceLight` becomes `DemoLaunch.forceAppearance` and reads `SEMPERE_DEMO_APPEARANCE` (`light` default,
  `dark`), so the demo does not pin its windows to light when a dark shot is wanted. The tests pass it through `launchEnvironment`.
  `DemoLaunchTests` (`Apps/Sempere/SempereAppTests/DemoLaunchTests.swift`) gains a case for each.
- The pages inside the notes: see the open question. With the recommendation, no setting changes and the paper stays
  light inside dark chrome, which is what a user sees by default (the canvas forces light; `Sempere.notePages` defaults
  to light).
- Only the guide shots with chrome get twins (welcome, new vault, settings, search, the palette shots, the new
  Watch and join shots). The viewer shot (`viewer-kepler`) is the web viewer, which has its own theme and is captured in
  its dark theme through the viewer's own switch in `scripts/viewer-shots.mjs`.

## 4. Tests

There is no oracle for how a screenshot looks; the checks are about the machinery.

- `DemoLaunchTests`: the appearance variable (light default, dark, an unknown value falls back to light).
- A shell test for the script's pure parts, `scripts/test-screenshots.sh`: with a fake `xcrun` and `xcodebuild` on
  `PATH`, a dark run sets the dark appearance, names the right output folder and exports the right variable; a size
  mismatch fails.
- `ScreenshotTests`/`DocsScreenshotTests` assert nothing by design, but each new shot waits for the control it needs
  (`undoButton` enabled and `redoButton` enabled; the Add Device sheet's nearby row; the join screen's six words), as the
  existing shots wait for theirs, and logs `SHOTDEBUG` on a miss.
- Site: `pnpm build` passes; a build check (a small script in `scripts/`) fails when a `-dark` entry in `media.json` has
  no file, when a `ThemedImage` pair differs in size, or when a dark file exists without a light one. A headless browser
  check (the site already builds with Astro; a Playwright script is the tool the web viewer uses) loads `/docs/use/watch/`
  with `prefers-color-scheme: dark` and with `data-theme="light"` set, and asserts from the network log that exactly one
  of the pair was requested in each state, and the other after toggling.
- Every PNG is looked at before it is used, as `docs/appstore/screenshots.md` already requires, and nothing in a demo
  reads as a real word or a real name.

## 5. Open questions, with recommended answers

1. **Note pages dark (Settings ▸ Appearance ▸ Note Pages ▸ Dark), or light paper in dark chrome?** Light paper in dark
   chrome for every twin. It is what a user sees by default and what the guide's text describes; it keeps the ink colors
   the way they are stored. Dark pages are an option worth one extra website shot, on the page that explains the
   appearance setting (`settings.mdx`), taken with `Sempere.notePages=dark` through a launch argument
   (`-Sempere.notePages dark`). Recommendation against dark pages everywhere: it makes the twins look like a different app
   from the default the store listing shows.
2. **Fold Undo into `01-write` and `02-sketch`, or add a seventh store shot?** Fold it in; six shots, the first three carry
   the feature.
3. **A dark App Store set?** Not in 1.2.
4. **A dark hero video?** No, see 3.3.
5. **Timing.** The App Store shots are needed for the 1.2 submission; the website shots and twins can follow the
   release, so the site PR does not block it.
6. **Watch simulator size.** Unverified: which watch the newest watchOS simulator offers on the machine that runs this.
   The script reads the size from the first shot instead of hard-coding it.
