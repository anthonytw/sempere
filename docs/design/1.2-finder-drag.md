# Drag a note to the Finder (Mac, issue #10) (1.2)

Status: design, 2026-11-13. Paths are relative to the repository root. The history before the repository's cut-over
(the 1.0 PR that hid the setting) is not in this repository's git log; what follows rests on `docs/mac.md` "Drag a
note out as PDF (not in v1)" and "Debugging a drag out", which record it.

## 1. Goal

On the Mac, dragging a note row from the list onto a Finder window or the Desktop leaves `<title>.pdf` there, while
the app runs. The Settings ▸ General ▸ Drag to Finder section (PDF, Markdown or HTML) is shown again.

Non-goals: dragging several notes as one archive (bulk export covers it: File ▸ Export to Folder or Zip…), dragging
into other apps' windows as anything but a file, iPad (it has no Finder; Files drops are a separate matter).

## 2. What exists and what 1.0 found

- The row's drag offers the note's file through an `NSItemProvider` with `registerFileRepresentation(forTypeIdentifier:
  fileOptions: [], visibility: .all)`, a suggested name, and the app's own payload for sidebar drops
  (`NoteFileDrag.register`, `Apps/Sempere/SempereApp/NoteFileDrag.swift`; `NoteDragProvider.make`,
  `NoteDragSource.swift`). `AppModel.prepareExport(noteID:)` (`Sources/SempereAppCore/AppModel/AppModel+DragExport.swift:25`)
  saves pending ink and downloads the note when the drag starts; the file request waits for it, renders with
  `SempereRender.PDFWriter` and writes under `$TMPDIR/SempereExport/<model id>/<random id>/<title>.pdf`
  (`PreparedExport.write`), never on the main thread (CLAUDE.md "Dragging a note out"; `MacDragOutTests`,
  `Apps/Sempere/SempereAppTests/MacCatalystTests.swift:144`, proves the file arrives while the main thread is blocked).
- Two row styles exist: SwiftUI `onDrag` (shipped) and a row-owned `UIDragInteraction` (`NoteDragHandle`). Both reach
  the same provider code.
- Build 12 on a real trackpad (docs/mac.md "Round 1"): UIKit writes a proper file promise to the drag pasteboard
  (`com.apple.NSFilePromiseItemMetaData`, `promised-file-name`, `promised-file-content-type`, `com.adobe.pdf`), but the
  Finder never reads it. No pasteboard access by the Finder, no green plus, the drag ends with operation 0, and every
  Finder drag message is logged `Reentrant message: …, current message: kDragIPCWithinWindow`, also for the first
  message. The file is asked for only when Sempere quits, when the pasteboard flushes its promises.
- Four hidden runs exist (`NoteDragTestRun` A to D, `Sources/SempereAppCore/Preferences/NoteDragDiagnostics.swift`):
  A `onDrag`, B `uikit`, C `onDrag` with a small text file written at drag start instead of the note, D `uikit` with
  the in-app payload left off. "Round 2" (relaunch the Finder, drag from another app as a control, then from Sempere)
  is described in `docs/mac.md`, but its results are not recorded anywhere in the repository. **Not verified:** whether
  C and D were ever run and what they showed.
- XCUITest's pointer drops nothing into the Finder (its drag test was deleted because it could not tell a fix from
  the bug), so no automated check exists.

So the open facts are two: the Finder rejects what Catalyst's UIKit bridge makes of a file promise (cause unknown),
and nothing automated can tell a working drag from a broken one.

## 3. Design

The work is an experiment ladder with an automated oracle, not a guess at the fix. Each rung is cheap, and the first
that passes the oracle ships.

### 3.1 The oracle: an automated drop into the Finder (first PR)

A script, `scripts/mac-drag-probe.sh` with a small Swift tool under `tools/mac-drag-probe/` (a package executable, not
in the app; built only by the script), run in the Mac runner's session (the same one that already runs
`scripts/app.sh test-mac-ui`, which needs a window server and Accessibility permission for the test runner):

1. Launch the debug app on the demo vault with the sidebar and note launch variables, in the window size
   `SEMPERE_DEMO_MAC_WINDOW` pins (`docs/appstore/screenshots.md`).
2. Make a temp folder and open it in a Finder window at a known place (`open -a Finder <folder>` and an AppleScript
   or `NSWorkspace` call that sets the window's bounds).
3. Find the note row's screen point from the app's accessibility tree (`AXUIElement`, the row's title) and the Finder
   window's target point from the Finder's.
4. Post `CGEvent` mouse down, a path of mouse-dragged events, and mouse up. A synthetic drag from `CGEvent`s is what a
   real pointer produces for AppKit's drag machinery, unlike XCUITest's, which is the reason the old test failed to
   discriminate.
5. Wait up to 20 seconds for `<title>.pdf` in the temp folder. Pass: the file exists, starts with `%PDF-`, and its page
   count equals the note's pages (`PDFKit` or `pdfinfo`). Also record the unified log's `drag` category for the run
   and fail on the `kDragIPCWithinWindow` reentrancy line, so a fix that works by accident is still named.
6. Run the same drag from a control source (TextEdit's title-bar proxy icon, or a file dragged out of a Finder
   window into another) first, to prove that the harness itself can drop a file into a Finder window on this machine.
   A harness that fails its control reports "harness cannot drop", never a verdict on Sempere.

The script prints a table (run, result, time to file) and exits 1 on a verdict of "no file". It is a tool run by an
agent or by hand, not part of the PR gate (like `scripts/screenshots.sh`); the Mac runner already used for `test-mac-ui`
is where it runs in `scripts/local-ci.sh --testflight`.

Where this cannot run (no Accessibility permission, no window server in the environment) the PR says so and the item
stays at the cut line; it is never replaced by a device step.

### 3.2 The ladder

Run each rung through the oracle; stop at the first pass.

- **E1: record the control runs.** Run A, B, C and D (the existing switches, set by environment variable in a debug
  build) through the oracle and write the table into `docs/mac.md`. C tells whether the Finder takes any file from this
  drag at all; D tells whether the in-app payload next to the promise is what it rejects. If C passes, the cause is in
  the PDF promise (type, name, delay); if C fails, the cause is the drag session itself and only E3 can help.
- **E2: a real file URL, ready before the drag.** `NSItemProvider(contentsOf: fileURL)` or
  `registerFileRepresentation(… fileOptions: [.openInPlace])` of a file that already exists when the drag begins,
  instead of a promise. The Finder reads a file URL from the pasteboard in the oldest, most compatible way. The
  cost is that the PDF must exist when the drag starts: render ahead of time. Prefetch `prepareExport` and the write
  when a row is selected or hovered for 300 ms, keyed by note id and revision names (so an edit voids it), kept per
  model under `exportFolder` and purged with it (CLAUDE.md "Dragging a note out"). A drag that starts before the file
  is ready falls back to today's promise. A row's drag adds no main-thread work: the closure only looks up a ready URL.
- **E3: an AppKit drag source.** A Catalyst app cannot link AppKit types, which is why `SempereStatusItem` is an AppKit
  bundle the app loads and talks to by notifications (CLAUDE.md "The Mac menu-bar item"). A second bundle,
  `SempereDragOut`, would start `NSView.beginDraggingSession(with:event:source:)` on the window's content view with an
  `NSFilePromiseProvider`, taking `NSApp.currentEvent` at the mouse down. Costs: a new target in `project.pbxproj`, an
  entitlement review (`scripts/release-check.sh` tables), the status-item rule "no logic" relaxed for this bundle,
  and the in-app sidebar drops, which UIKit's drag session serves, would need the AppKit session to carry the app's own
  payload in a type the UIKit drop side reads (unknown whether the bridge delivers an AppKit-started drag to a UIKit
  drop target). Only if E1 shows the drag session itself is the problem and E2 fails.

Whatever passes also fixes the provider for Markdown and HTML (`DragExportFormat`, one `UTType` per format,
`NoteFileDrag.fileType(for:)`), and the oracle runs each format once.

### 3.3 Turning it on

When a rung passes: `DragExportFormat.showsInSettings` becomes true (the one line `docs/mac.md` names, with its
localized strings in `DragToFinderSettingsSection`), `docs/mac.md` "Drag a note out as PDF" loses "not in v1", the
diagnostics section keeps its runs (they stay the way to debug a regression), and a changelog fragment says "Drag a note
from the list to the Finder."

### 3.4 CLI

Nothing here reads or changes vault data. The CLI already exports a note the same way (`sempere export`), with the same
renderer, so the file's bytes are covered by the existing export tests.

## 4. Tests

- Linux and package: unchanged (`ExportFileName`, `PreparedExport.write` and the epoch/generation checks are covered in
  `Tests/SempereAppCoreTests`).
- E2's prefetch cache (`SempereAppCore`): hit and miss by revision names, voided by an edit or a remote merge, purged
  with the vault, bounded in count and bytes (a note's PDF can be large), the drag never waits on it. Tests on
  `TestHost`; the cache logic is not Apple-only.
- `MacDragOutTests` (existing) keeps the "file arrives while the main thread is blocked" check for the promise
  fallback, and gains the same check for the ready-file path (no main-thread dependence at all).
- The oracle itself (section 3.1) is the end-to-end test. Its results go in the PR description. It needs the
  Accessibility permission for the process that runs it; the PR names the machine it ran on.

## 5. Open questions, with recommended answers

1. **Which rung first?** E1 (record what the existing switches show), then E2. E3 only if both fail. E1 costs no code.
2. **Is a drag that waits for a late render acceptable?** The ready-file path covers selected or hovered rows. A drag
   from an unselected row that starts at once falls back to the promise, which on a working Finder takes however
   long the render takes; the app shows no spinner in the drag. Recommendation: accept; it is the same as 1.0's design.
3. **Show the setting again only when the oracle passes?** Yes. It stays hidden if no rung passes, and issue #10 stays
   open with the table in `docs/mac.md`.
4. **Does the file sit in the container's temp folder (sandbox)?** Unverified: whether the Finder can read a file URL
   under the app's container for a plain URL drop. A promise avoids the question (the destination grants the write);
   a file URL does not. The oracle answers it; if the Finder refuses, E2 copies into a folder the Finder can read
   (the promise's own destination is the safe place, which is the promise again).
